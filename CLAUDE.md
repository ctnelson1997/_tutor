# CLAUDE.md — Project Instructions for Tutor

## Documentation Policy

When making codebase changes (new engines, scripts, store fields, utilities, architecture, dependencies, etc.), update **README.md** and **CLAUDE.md** in the same commit to keep documentation current. Do not let docs fall out of date.

## What This Is

A **client-side-only** React app that visualizes code execution step-by-step. Students write code in a CodeMirror editor and see call stack, variables, heap objects, and console output at every line. No backend — everything runs in the browser.

The architecture supports **multi-language builds**: each language has a `LanguageEngine` under `src/engines/`, and the Vite build system produces a standalone single-language site per target. Each target deploys to its own domain (e.g. jstutor.org, pytutor.org).

### Quick Instrumenter Testing

To inspect instrumented output without running the full test suite, use `npx tsx -e` with a direct import. This is the fastest way to verify instrumentation changes:

```bash
npx tsx -e "import { instrument } from './src/engines/js/instrumenter'; console.log(instrument('let x = 1;\nconsole.log(x);'));"
```

- **Import path**: `'./src/engines/js/instrumenter'` (no `.ts` extension, relative from project root)
- **Use single quotes** inside the JS source string passed to `instrument()`, or escape double quotes
- **The output is the full instrumented JS source** — look for `__capture__`, `__pushFrame__`, `__popFrame__`, `__condition__`, and `__loopCount` calls
- To check specific details, filter the output:
  ```bash
  npx tsx -e "import { instrument } from './src/engines/js/instrumenter'; const out = instrument('function foo() { return 1; }\nlet x = foo();'); const match = out.match(/__capture__\((\d+)/); console.log('first capture line:', match[1]);"
  ```

## Architecture

```
User code
  -> LanguageEngine.execute(source)
    -> [language-specific pipeline]
    -> ExecutionSnapshot[]
  -> Zustand store
  -> React UI (language-agnostic)
```

### Build-Time Language Targeting

Each build bundles **only one language engine**. Controlled by:

- **`.env.js` / `.env.py` / `.env.java`** — per-language env vars (name, color, domain, tagline)
- **`src/config/branding.ts`** — reads `import.meta.env.VITE_*`, single source of truth for all UI branding
- **`src/engines/registry.ts`** — conditionally registers only the target engine based on `import.meta.env.VITE_LANGUAGE`; Vite tree-shakes the unused engine's code out of the bundle
- **`vite.config.ts`** — function form; detects `js`/`py`/`java` and `viewer-<lang>` modes, manually loads the matching `.env.<lang>` via `loadEnv`, exposes those values through `define`, and conditionally enables `vite-plugin-singlefile` + a `rename-viewer-output` hook for viewer builds

All hardcoded branding references and `#DD030B` colors have been replaced with `branding.*` imports. To add a new language target, create a new `.env.<lang>` file and add corresponding `dev:<lang>` / `build:<lang>` / `build:viewer:<lang>` scripts.

The **dispatcher** at `src/engine/executor.ts` is a thin layer that reads `language` from the store, calls `getEngine(language)`, delegates to `engine.execute()`, and updates the store. All UI components import `runCode` from here.

**The result contract (`WorkerMessage` in `src/types/snapshot.ts`, #7).** Every engine replies `{ type: 'result', snapshots, error? }` once the program has run, even if it ended early. `error` is a `RunError` with these fields:
- `message`;
- `line`: where it happened, which the editor marks;
- `kind`: `'exception'` (an uncaught exception), `'limit'` (the step cap or time budget), `'error'` (the engine stopped it: an unsupported construct, an internal failure) or `'compile'` (a Java program javac would reject, #23, or a JS program that doesn't parse, #50, so nothing ran);
- `lines`: for a compile error, the line of each error, in javac's order;
- `stderr`: what the program's stderr would show, such as Java's stack trace, Python's traceback or javac's errors, shown in the console at the last step.

`{ type: 'error', message, line? }` is only for failures before anything ran: a Python syntax error, the engine failing to load, or the worker's 10-second timeout (a Java program that doesn't compile, or a JS one that doesn't parse, is a result with no steps and a `compile` error). The dispatcher sets the snapshots first and then the error, because `setSnapshots` clears `error`. The UI treats an error that has snapshots as belonging to the last step:
- `EditorPanel` shows the banner (warning-colored for `limit`, "Compile error" for `compile`, the message's line breaks kept) and marks each of `errorLines(error)` with `.cm-error-line`: every compile error's line, else `error.line`. With several compile errors the banner adds "n more errors listed in the console" (`moreErrorsNote`).
- `ConsolePanel` shows the step's `console` when the program wrote to stderr or read stdin (stdout and stderr lines in program order, stderr in red; #22; what Python's `input()` read, echoed after its prompt in teal italics, `ConsoleLine.input` ranges split by `consoleSegments`, #32), else `stdout`, and appends the error's `stderr` in red (an uncaught exception's trace, or javac's listing).
- `ControlBar` adds a link ("ends with an exception" / "stopped early") that jumps to the last step.
The labels live in `src/utils/runError.ts`. The console keeps whitespace (`white-space: pre-wrap`), so `printf` padding and stack traces line up.

### Adding a New Language

1. Create `src/engines/<lang>/` with an `index.ts` exporting a `LanguageEngine` object
2. Add a conditional registration block in `src/engines/registry.ts`
3. Expand `LanguageId` type in `src/types/engine.ts`
4. Create `.env.<lang>` with branding vars (`VITE_LANGUAGE`, `VITE_APP_NAME`, `VITE_BRAND_COLOR`, etc.)
5. Add `dev:<lang>`, `build:<lang>`, `dev:viewer:<lang>`, and `build:viewer:<lang>` scripts to `package.json`
6. Add the new language to the `LANGS` array in `vite.config.ts`

### Branding (`src/config/branding.ts`)

All UI branding (app name, colors, tagline, domain) flows from `import.meta.env.VITE_*` variables through a single `branding` object. Components import `branding` instead of using hardcoded strings. The env vars are set per build target via `.env.js` / `.env.py` / `.env.java` files loaded by Vite's `--mode` flag.

### Store (`src/store/useStore.ts`)

Zustand store with: `language`, `code`, `stdin`, `snapshots`, `currentStep`, `isRunning`, `error`, `hideFunctions`, `showReferences`. The `language` field defaults to `branding.languageId` and drives which engine is used and which editor extension / examples / sandbox code are shown. The `showReferences` flag enables Python's "everything is an object" visualization mode, where primitives are promoted to heap objects via `src/utils/promoteToHeap.ts`. The `stdin` field holds the preset console input consumed by Java's `Scanner` and Python's `input()` (#32) — it is edited via the `StdinPanel` (shown in the editor column for an engine that declares `LanguageEngine.stdin`, a `StdinDescription` naming its reader and the textarea's hint: Java and Python), passed to `engine.execute(source, { stdin })` by the dispatcher, and threaded into the Java interpreter's constructor or the Python worker's `run_traced(source, stdin)`. `error` is a `RunError` (see the result contract above); alongside snapshots it describes how the run ended, at the last step. `setSnapshots` stores the steps through `shareSnapshots` (see the snapshot sharing note), so consecutive steps share their unchanged parts whatever engine made them.

HashRouter with routes:

### Standalone Viewer (`viewer.html` + `src/viewer-main.tsx`)

The export feature ships a parallel entry point that runs without React Router. `viewer.html` (at the project root) is the HTML input for the `viewer-<lang>` build mode; `src/viewer-main.tsx` reads `window.__EXAMPLES__` (an array baked into the HTML by the export feature) and mounts `<ViewerApp />`. `ViewerApp` renders its own minimal navbar (brand + `ExamplePicker` when 2+ examples are present), then delegates to the existing `<App embed viewer />` for the rest of the layout.

`App` accepts a `viewer` prop in addition to `embed`. `ControlBar` treats `embed || viewer` as the condition for hiding Share/Embed/Export; the "Open in `<AppName>`" link points to `https://<branding.domain>` in viewer mode (rather than the share URL it would generate in embed mode).

The full app — engine included — is bundled into the single viewer HTML, so users opening an exported file can edit code and re-run the visualization with `runCode()` like in the live app.

### Export Feature

- **Trigger**: Export button in `ControlBar`, next to Share/Embed (hidden in `embed`/`viewer` modes). Opens `src/components/ExportModal.tsx`.
- **Offline use** (#36's decision): the JS and Java viewers carry their engines, and an exported Python file shows its recorded steps offline, but running Python code in it loads Pyodide from the CDN (bundling it would make each file about 19.6 MB instead of 1.1 MB). The dialog says so for Python (`offlineNote(language)` in `exportHtml.ts`), and the worker's load failure says the engine needs an internet connection.
- **Pipeline**: `ExportModal` → `runCode` (if no snapshots yet) → `fetchViewerTemplate('./viewer-<lang>.html')` → `buildExportHtml(template, example)` → `downloadHtml(...)`. All splicing logic lives in `src/utils/exportHtml.ts`.
- **Template placeholder**: `viewer.html` contains `/* EXPORT_PLACEHOLDER_START */ window.__EXAMPLES__ = []; /* EXPORT_PLACEHOLDER_END */` inside a `<script id="tutor-examples">` block. `buildExportHtml` replaces the assignment between those markers with a single-example array (the markers themselves are preserved so future appends remain easy).
- **Multi-example merge**: users hand-edit the EXAMPLES array of an exported file to append entries from other exports. `ExamplePicker` shows a navbar dropdown when the array has 2+ entries.
- **Worker inlining**: the Python and Java executors import their workers via `?worker&inline` (`import PyWorker from './worker.ts?worker&inline'`). This causes Vite to serialize the worker as a base64 blob URL inside the singlefile bundle — required for the standalone HTML to run without external chunks. The same import works in the main builds too (just chunked there).
- **Engine versioning**: the `tutor-engine-version-marker` plugin in [vite.config.ts](vite.config.ts) tags the inlined module `<script>` with `data-tutor-engine="X.Y.Z"` (read from `package.json` at build time), injects `window.__TUTOR_ENGINE_VERSION__=...` at the very top of that script's body, and prepends a multi-line HTML comment with explicit upgrade instructions (download a fresh `viewer-<lang>.html`, replace just the data-tutor-engine script block, EXAMPLES survives). The version is also shown in the viewer's navbar as `engine vX.Y.Z`. The main app's [AppFooter](src/components/AppFooter.tsx) reads the same value via the `__TUTOR_ENGINE_VERSION__` compile-time constant injected by `define`.
- **Data schema versioning**: `CURRENT_EXAMPLE_SCHEMA_VERSION` in [src/types/viewer.ts](src/types/viewer.ts) is the contract version of the `ViewerExample` shape (currently `2` — `2` added the optional `stdin` field so exported Java `Scanner` programs re-run with their original input; `ExportModal` reads `stdin` from the store and `viewer-main.tsx` restores it). `buildExportHtml` stamps it into every payload; `viewer-main.tsx` compares each example's `schemaVersion` against the constant and passes a `schemaMismatch` flag down to `ViewerApp`, which renders a dismissible warning alert when an example was produced by a newer engine than what's running. Bump the constant when adding required fields to `ViewerExample` or to `ExecutionSnapshot` so previously-exported files can't masquerade as the new shape. The optional `error` field (how the recorded run ended, #7) was added without a bump, since an older viewer still shows the steps; `ExportModal` writes the store's error, and `viewer-main.tsx` / `ExamplePicker` restore it (and `stdin`). A primitive's optional `display` text (#17) came without a bump too: exported snapshots without it render by type. So did a snapshot's optional `console` (#22): without it, the console is `stdout`. So did a `RunError`'s `compile` kind and `lines` (#23). So did a snapshot's optional `label` (#45): without it, a step shows no label.
- **Splice safety**: `buildExportHtml` uses `lastIndexOf` to locate the `tutor-examples` script tag, AND assembles the marker strings from concatenated char fragments in source (`'<' + 'script id="tutor-examples">'`). Both guard against the same `exportHtml.ts` source being bundled into the engine: if the regex source or error messages contained the literal marker text, the splice could false-match inside the engine bundle and corrupt it. The `ignores marker strings that appear inside the bundled engine source` test in [exportHtml.test.ts](src/utils/__tests__/exportHtml.test.ts) covers this regression.

## TypeScript Constraints

- **`erasableSyntaxOnly: true`** — No `enum`, no parameter properties (`constructor(readonly x)`), no `namespace`. Use `type` unions and plain class fields instead.
- **`verbatimModuleSyntax: true`** — Use `import type` for type-only imports.
- **`noUnusedLocals` / `noUnusedParameters`** — Prefix unused params with `_` if needed.
- Test files (`__tests__/`) are excluded from `tsconfig.app.json` via the `exclude` array — they use Node APIs (`node:vm`) that aren't in the app's type scope.

### JDK differential suite (Java)

The Java engine re-implements Java, so it's tested against real `java`. This is the acceptance test for the Java overhaul (roadmap: GitHub issue #3; this suite is #4). Everything lives in `src/engines/java/__tests__/jdk/`:

- **Cases.** `cases/<category>/<name>.java`, with an optional `<name>.stdin` for `Scanner`. Categories: `realistic/` (typical CS1/CS2 programs), `core/`, `collections/`, `oop/`, `misc/`, `extra/` (targeted checks), and `compile-errors/` (programs `javac` rejects). Every example in `examples.ts` is also a case, `examples/<slug>`, read live; its directory holds only goldens. So **adding or editing a Java example means regenerating its golden** (`npm run test:java:golden -- examples/<slug>`), or `npm test` fails. The case id `<category>/<name>` is the key everywhere.
- **Goldens.** `<name>.golden.json` is `{ stdout, stderr, exitCode, exception: { class, message } | null, compileError, sourceSha256 }`. `npm run test:java:golden` ([scripts/java-golden.ts](scripts/java-golden.ts)) writes them. It refuses any JDK but 21 (set `JAVA_BIN` to pick one) and runs each case as `java Main.java` (the single-file source launcher runs the **first** top-level class, so put `main`'s class first) in a temp dir, 8 at a time, with a 30 s timeout. Line endings are normalized and source-launcher stack frames are stripped from stderr. Goldens are committed, so `npm test` needs no JDK. `sourceSha256` hashes the source and stdin: editing a case without regenerating fails the suite's "golden is current" test and skips that case. A full regeneration also deletes orphaned goldens.
- **Output check** (`compareOutput` in [harness.ts](src/engines/java/__tests__/jdk/harness.ts)). It compares the last snapshot's stdout with the golden's (one trailing newline dropped on both sides). It also checks whether an exception escaped, and its simple class name: the interpreter reports `Exception in thread "main" X: msg` for a `throw` and `Line N: X: msg` for built-in errors. A `compile-errors/` case passes only if the interpreter errors with zero snapshots; a separate test checks that `runJava`'s listing is the golden's `compileError` (javac's diagnostics), byte for byte. A failure is either **wrong** (no interpreter error, which is the harmful kind) or **error**.
- **Snapshot invariants**, one test each per case: `refs` (every value is well formed and every ref resolves in the same snapshot; this catches sparse-array holes), `lines` (1..N), `js-errors` (no raw JavaScript error text such as "Cannot read properties" or "Maximum call stack"), `scopes`, `reachable` and `statics`. `scopes` checks that block-scope frames of the innermost method only show locals whose lexical scope contains the step's line; ranges come from the CST via `blockScopedDeclarations`, and frames are matched to methods by name (constructors by class name). It flags extra variables, not missing ones. `reachable` checks that every heap object is reachable from a frame's variables, `this` or the static fields. `statics` checks that every step starts with a "Static fields" frame showing each static field of the entry class (`staticFieldsOf` reads them from the CST), and that a program with no static field (interface constants count) has no such frame. All six are in `ENFORCED_INVARIANTS`. A new invariant can start outside it while its failures are fixed; `scripts/java-diff.ts` reports its count either way.
- **Known failures.** `known-failures.json` has two maps. `output` maps case id → `{ issues, reason }`, and `invariants` maps case id → invariant → `{ issues, reason }`. `issues` lists the roadmap issue(s) the failure waits on, main one first. Listed checks run as `it.fails`, so the suite stays green, and a fix that makes one pass turns it red: delete the entry. A check that newly fails needs a fix, or an entry naming the issue that fixes it. `scripts/java-diff.ts` prints every difference with its issue tag, flags entries that are missing or out of date, and exits 1 if any are.
- **Fail loudly (#6's guard).** When a known failure's main issue is in `LOUD_FAILURE_ISSUES` (#6 syntax, #15 inheritance, #16 enums/records/inner and anonymous classes/lambdas), the construct is one JavaTutor rejects. So the case also gets a normal test, "fails with an error, not wrong output", and `java-diff` flags it if it prints wrong output. A program the engine can't run must stop with an `UnsupportedFeatureError`, never print a plausible wrong answer.
- **Summary.** The suite prints pass / wrong output with no error / error counts. Vitest's agent reporter (auto-selected when run by an AI agent) hides console output from passing tests, so pass `--reporter=default` to see it: `npx vitest run src/engines/java/__tests__/jdk --reporter=default`.
- **Workflow for fixing a roadmap issue.** Run `npx tsx scripts/java-diff.ts`, find the cases tagged with the issue, fix them (`scripts/java-viz.ts <case id>` shows every step), run the suite, and delete the entries that now pass. Add a regression case to `cases/` for anything the corpus didn't cover.

### CPython differential suite (Python)

PyTutor runs real CPython (Pyodide), but traced, and the tracer decides what each step shows, so it is tested against CPython itself (#29, the first step of the PyTutor roadmap #28). Everything lives in `src/engines/py/__tests__/cpython/`:

- **Cases.** `cases/<category>/<name>.py`, with an optional `<name>.stdin` for `input()`. Categories: `realistic/` (typical CS1/CS2 programs, 15 of them reading input), `data-structures/`, `exceptions/`, `extra/`, `functional/`, `limits/` (the step cap, deep recursion, endless loops), `numbers/`, `oop/`, `print-format/`, `scope-mutation/`, `stdlib/`, and `syntax-errors/` (programs CPython rejects). Every example in `examples.ts` is also a case, `examples/<slug>`, read live, so **adding or editing a Python example means regenerating its golden** (`npm run test:py:golden -- examples/<slug>`).
- **Goldens.** `<name>.golden.json` (`PyGolden` in `corpus.ts`): `stdout`, `stderr` and `console` (each line with the stream that wrote its first characters, in program order, as `python -u main.py` shows it), `exception` (class and `str()`), `traceback` (`traceback.format_exception`, the user's frames only, source lines from `linecache`), `compileError` (class, message, line, offset and CPython's display), `endless`, `events` (the reference trace, at most 8,000: each `call`/`line`/`return`/`exception` event of the user's frames, with the stack of their code names and each variable's reference repr, `_r`: the `repr()` of a None, bool, int, float, complex or str, `<int with N digits>` past the digit limit, `<TypeName>` otherwise; a module frame shows its globals), `truncated`, `stepEvents`, `finalGlobals`, `continuation` (lines inside a multi-line statement) and `sourceSha256` (source and stdin). `npm run test:py:golden` ([scripts/py-golden.ts](scripts/py-golden.ts)) writes them; it refuses any `pyodide` but `PYODIDE_VERSION` and records each case in a process of its own (`--record <id or file.py>`, `record.ts`): a fresh Pyodide with `PYTHONHASHSEED=0` (a set of strings would otherwise print in another order in each interpreter), unbuffered streams, the program's stdin, the reference tracer (`REFERENCE_TRACER`) stopping an endless program after 5 s; then the program again untraced, whose output and exception the golden keeps and which must agree with the traced run. The reference tracer marks a `return` event that is the frame unwinding (`unwinding`: an exception passed through it since its last line event, or it stopped at an instruction other than `RETURN_VALUE`, `RETURN_CONST` or `YIELD_VALUE`, as after a finally block or an inlined comprehension's cleanup re-raised), reads a module frame's variables from `f_globals` (never `f_locals`, which 3.12 merges with an inlined comprehension's hidden slots), skips `f_locals` in a class body with an inlined comprehension (3.12 warns `assigning None to unbound local` when tracing writes it back; such events record `!unreadable`), keeps its own copy of the builtins (a program replacing `builtins.str` doesn't change `_r`), and keeps the recursion limit `python main.py` has: the module frame is depth 1 (Pyodide's and the recorder's frames below it, `_base`, don't count: the real limit is the program's plus `_base`, and `sys.getrecursionlimit`/`setrecursionlimit` show the program its own), and while tracing the real limit is 50 higher still, for the trace function's own frames, with `_trace` raising CPython's RecursionError for a frame deeper than the program's limit (re-enabling tracing through a one-shot profile hook, since CPython turns it off when a trace function raises).

The CPU time (`process.threadCpuUsage`) is only reported.

## Key Design Notes

- **Single-language builds** — each build bundles only its target engine; tree-shaking removes unused engines
- **JS engine**: Native JS in disposable blob-URL Web Workers — fresh global scope each run
- **Python engine**: Pyodide (CPython compiled to WASM) in a persistent module Web Worker, each program in a fresh interpreter restored from a memory snapshot (#35, `session.ts`) — `sys.settrace()` intercepts execution events to build snapshots; Pyodide is loaded eagerly from CDN at page load
- **Java engine**: `JavaInterpreter` (`interpreter.ts`) runs a program in a disposable Web Worker, in three stages: java-parser's CST becomes an AST (`ast/`, #12), the binder resolves names, types and overloads into a bound tree (`semantic/`, #13), and the evaluator runs that tree (`eval/evaluator.ts`, #14). A program the binder rejects stops before any step: with an `unsupported` diagnostic's "… aren't supported in JavaTutor yet" (the first in the source, preferred), else with javac's errors, all of them in javac's order (see the compile errors note). It supports primitives, strings, text blocks, arrays of any dimension (`new int[2][3][4]`, `new int[3][]`) and their initializers, classes with fields, constructors and initializers, nested static classes, interfaces with constants and static methods, inheritance (#15), inner, local and anonymous classes, enums, records, lambdas and method references (#16), overloads and constructors chosen by argument type, varargs, generics (type-checked, erased when running), boxing with the Integer cache, primitive and checked reference casts, recursion, and Java's statements (see the classes and statements notes below).
- **The Java core's stages (#11 chose a rewrite: #12 → #13 → #14).** Stage 1 (#12, `src/engines/java/ast/`) is the AST: `parseAst(source)` parses with java-parser and converts each grammar rule once (`convert.ts`). Binary expressions arrive flat (one node of operands and operator tokens, assignment and `instanceof` included) and are rebuilt by precedence climbing; shifts are java-parser's `shiftOperator` nodes of adjacent `<`/`>` tokens. A dotted name stays one `Name` (#13 classifies its parts per JLS §6.5), but a call's method name is split off (`a.b.c(x)` is a MethodCall of target `a.b`), and `super` becomes a `Super` node. `var` (which java-parser reads as a class named var) is a `VarType`. Parentheses are kept as `Parens`, and every node has a `Range` (offsets, plus 1-based line and column of its first and last character). Anything the conversion doesn't handle becomes an `Unsupported` node with its source, never a gap. `printAst` prints the tree back, adding only the parentheses its shape requires, so a wrongly shaped tree wouldn't print the original tokens: the corpus test relies on that. Stage 2 (#13, `src/engines/java/semantic/`) binds the AST: `bindProgram(unit)` returns the bound tree (`bound.ts`) and diagnostics. `library()` parses `stubs.ts` once into library ClassSymbols (a method missing from the stubs is still callable if the JDK class has a method of that name, `jdkHasMethod` over the generated `jdkMembers.ts`: the binder gives it a dynamic type, `BDynamicCall`, and the stdlib finds it by name when the program runs; a name the JDK class lacks, `s.lenght()` or `arr.length()`, is javac's "cannot find symbol"; `$any` in a stub is a parameter that takes anything as it is, for overload families like `Arrays.toString`). Declarations become ClassSymbols with type parameters, supertypes (a class without `extends` gets Object), fields, methods and constructors (a default one when none is declared); any library class can be named without an import (JavaTutor is lenient), user classes first. In bodies, names are classified as JLS §6.5 does (local, field through `this` or of a class, type, package), member types are substituted through the receiver's type arguments (raw receivers see erased members), and calls choose an overload as §15.12.2 does: strict, then loose (boxing), then variable arity, the most specific winning, generic type arguments inferred from equality, lower (`? extends T`, plain arguments) and upper (`? super T`) bounds, then the expected type; a diamond takes its arguments from the target type, else the constructor's arguments, else stays raw. Conversions are explicit `BConvert` nodes (widen, narrow, box, unbox, checkcast); a value of dynamic type converts with a checkcast. `==` on two references is `BRefEquals` (identity), numeric when either side is primitive. Constant expressions (literals, constant variables, operators on them, a concatenation of constants) fold to `BConst`, except where Java would throw (`1 / 0`). Diagnostics are `error` (javac's message: incompatible types, lossy conversion, bad operand types, cannot find symbol, wrong arguments, ambiguous references, literals out of range, `not a statement`, and #23's flow errors) or `unsupported` (a declaration JavaTutor rejects, with its message: annotation types, extending a library class other than Object and the exceptions, two classes with one name, methods and fields outside a class). Unsupported expressions and statements (`X.super.m()`, record patterns, an anonymous subclass of a collection class, a lambda passed to a library method the stubs lack) become `Unsupported` nodes the evaluator reports when it reaches them. The class model (#15) has javac's checks: cyclic inheritance (`checkCycles`, which also cuts the cycle), a final superclass, `extends` an interface or `implements` a class, an abstract method a concrete class doesn't implement (`checkImplemented`: an implementation is a non-abstract method of the class chain or a default method, with the abstract method's parameter types as seen from the class), and an override's return type (`checkOverrides`: the same primitive or void, or a subtype). `super.m()` binds to the superclass's method as a `special` call (no virtual dispatch) on `This` typed as the superclass (an abstract one is an error), `super.f` to the superclass's field. A constructor without `this(…)` or `super(…)` gets an `implicit` `super()` with the superclass's no-argument constructor (javac's error when there is none), unless the superclass is Object. An array's `clone()` has the array's type (JLS §10.7); `getClass()` returns a `Class<?>` (stubbed with `getName`, `getSimpleName`, `toString`), and a class literal (`String.class`, `int.class`) is a `BClassLiteral` named as `getName()` names it. #16's constructs:
  - **Enums** are classes extending `Enum<E>` (stubbed with `name`, `ordinal`, `compareTo`, …). Their constants are static fields with an `enumOrdinal`, made first in the enum's static initialization (`enumConstant` initializers, each with the constructor its arguments choose; a constant with a class body is an anonymous subclass, `Main$Op$1`). `values()` and `valueOf(String)` are `synthetic` methods. A switch label is a constant's name (qualified too, as Java 21 allows).
  - **Records** extend `Record`: each component is a final field, with an accessor, `equals`, `hashCode` and `toString` (each `synthetic` unless declared) and the canonical constructor (`synthetic`, or a compact one, which gets the components as parameters). java-parser reads a member record with an empty body as a method returning `record`; the AST turns it back (`recordFromMethod`).
  - **Inner, local and anonymous classes.** A local class (`localClass`) and an anonymous one (`newAnonymousClass`, named `Host$1` as javac numbers them, `flatName`) are bound where they appear, their code in a scope behind a capture `Boundary`, so it sees the enclosing locals: one read from inside is captured (`lookupLocal`) as a `val$x` field of the class (`captures`). An inner class's objects hold their enclosing instance in `this$0` (`outerField`; a local or anonymous class gets one only if it uses it, and none where there is no `this`, `staticContext`). An enclosing object's member is reached through `OuterThis` (`enclosingThis`, also `Outer.this`), and `new Inner()` / `o.new Inner()` give the object its `outer`. An anonymous class's constructor is its superclass's (`BNew.anonymous`).
  - **Lambdas and method references** become `BLambda` nodes against their target's function type (`functionType`, JLS §9.9: the single abstract method, wildcards as their bounds): parameters, body (a block, or an expression converted to the result type), the locals it captures (each must be effectively final: `checkEffectivelyFinal`, javac's "must be final or effectively final"), whether it uses `this`, and its javac name (`lambda$main$0`). A method reference is a lambda whose body calls the method (`Type::static`, `Type::instance` taking the receiver first, `expr::m` with the receiver evaluated once, `this::m`, `super::m`, `Type::new`, `int[]::new`). As arguments they are `Deferred` (`argExpr`): overload resolution only checks their shape (`potentiallyCompatible`: a functional interface whose method takes as many parameters), and `resolveDeferred` binds them once the method is chosen, refining its inferred type arguments: an explicitly typed lambda's parameters and an exact `Type::method`'s receiver fix them, and a lambda's result is a lower bound for what's left (`Comparator.comparing(p -> p.name)`). A generic call or diamond whose type arguments only the target can give (`Collectors.toList()`, `polyNodes`) is deferred too and bound again with its parameter type as target; a type variable matched only against `?` stands for the wildcard. A lambda needs a target: `var f = () -> 1` and `Object o = () -> 1` are javac's errors.
A library class JavaTutor knows of but lacks (`UNSUPPORTED_LIBRARY`: `Thread`, `LongStream`, `BigInteger`, …) has a dynamic type where it is declared, so what uses it is reported when it runs (`new Thread()`, the lambda assigned to it), and extending one is unsupported inheritance. Stage 3 is the evaluator, in the next two notes.
- **The Java evaluator (#14, `eval/evaluator.ts`)**:
  - **Frames on an explicit stack.** Each Java frame (a method, a constructor, a class's `<clinit>`) runs as a generator. A call yields the new `Frame` to `drive`, a trampoline that keeps the frames on `this.frames` and resumes the caller with the result, so JavaScript's stack doesn't grow with Java's recursion. Past `maxDepth` frames (1200 by default, so it comes before the 5000-step cap; tests raise it) a call throws a catchable StackOverflowError. A library callback (a user `toString()` for println, `compareTo()` for a sort, a lambda for forEach, through `invokeUserMethod`) runs a nested `drive` (`runNow`) that takes steps, as pythontutor.com shows such calls; only an uncaught exception's `toString()`, after the program ended, runs quietly.
  - **The program's code for a call** (`programCode`): a lambda's body (for its interface's method), a method of the receiver's class chain or a default method of its interfaces (`userMethod`), or a method javac generates (`synthetic`, run directly with no steps: an enum's `values()`/`valueOf()`, a record's accessors, `equals`, `hashCode`, `toString`). `callLibrary`, `callLibraryNow`, `callByName` and `invokeUser` all ask it first.
  - **Lambdas (#16).** Evaluating a `BLambda` makes a function object (`makeLambda`): it copies the captured locals (and `this`, and a method reference's bound receiver) and is drawn as an `objectType: 'function'` heap object labeled with its source, its fields the captured values (`receiver` and `this` included). A call runs `lambdaFrame`: a frame named as javac names the method (`lambda$main$0`), showing the captured locals (javac passes them as arguments) and the parameters, with an entry step, the body's steps and a return step with the value (converted to the function type's result, `samReturn`). A method reference's frame is `hidden`: no steps, not drawn, not in traces; only the method it calls shows. `functionShape` tells the stdlib which interface a function value implements.
  - **#16's objects.** Enum constants are made by `enumConstant` (an object of the enum or the constant's body class, `JavaObject.enumConstant`), drawn as `Planet.EARTH`, printed by name, compared by ordinal (also for the stdlib's natural ordering), matched by switch labels, and kept out of the "Static fields" frame. An inner object's `this$0` and a local or anonymous object's `val$x` fields are set before its constructor runs; a captured local is read from the frame, else from those fields along `this` and its enclosing instances (`slotOf`, `capturedSlot`), and `OuterThis` walks `this$0` (`outerThis`). An anonymous class's constructor runs its superclass's, then its initializers (`constructAnonymous`). A record's canonical constructor assigns the components; a compact one runs its body, then assigns them from its parameters. A for-each loop over a program's `Iterable` calls `iterator()`, then `hasNext()` and `next()` each time (`iteratorNext`), each a call that shows its frame. A class literal gives the same `Class` object as `getClass()` (`classObjectNamed`).
  - **Two ways to evaluate.** `isPure` marks the expressions that can't run the program's code: no user calls, user object creation, class initialization or switch expressions, and library calls only on receivers a user class can't implement (`libraryReceiver`: not Object, Throwable or a library interface such as Comparable). `pv` evaluates those by plain recursion; `gv`, the generator, evaluates the rest and yields frames.
  - **Calls.** The binder chose the overload. `callUser` checks the receiver (a NullPointerException), picks the override for a virtual call (`findOverride`, JLS §8.4.8: the supertype method's parameter types seen from the receiver's class, type arguments substituted, then erased, so `cmp(Point, Point)` overrides `Cmp<T>.cmp(T, T)`; the class chain first, then default methods of the interfaces it implements; cached in `overrides`) and pushes its `methodFrame`. A frame of a method the receiver's class inherited is labeled with its class (`Animal.describe`, `Greeter.greet`); stack traces use the method's own name (`Frame.method`). A `special` call (`super.m()`) runs the method it names; one to a library method (`super.toString()`, `super.equals(o)`, `super.hashCode()`, `super.clone()`) runs Object's own implementation (`objectMethod`, `ownString`), never the class's override.
  - **Objects of a class chain (#15).** An object holds the fields of its whole chain, superclasses' first (`layout`); a field hidden by a subclass field of the same name is kept under `Owner.name` (`fieldKey`, only when some class hides one, `hidesFields`). `getClass()` returns one `Class` object per class (`classObject`, so `getClass() == o.getClass()` compares classes) with `getName()` (`Main$Dog`, `java.lang.String`, `[I`), `getSimpleName()` and `toString()`; an array's `clone()` is a shallow copy; `super.clone()` copies a Cloneable object's fields and throws CloneNotSupportedException otherwise. A library method runs in the stdlib (`callLibraryNow`: `callStaticMethod`, or `instanceCall`, which sends strings to `stringMethod`, boxes to `boxedMethod`, a StringBuilder to `stringBuilderMethod`, `System.out`/`System.err` to `printStream`, collections to `callInstanceMethod`, then exceptions and Object's methods), unless the receiver's class implements it (`userMethod`). A library result is converted to the call's static type (`toStatic`: boxed where that is a reference type, unboxed where primitive). A `BDynamicCall` (a method the stubs lack) finds the method by name (`callByName`).
  - **Boxing.** `box` marks a primitive `boxed`, which gives it identity for `==` (`refEquals`). Values from -128 to 127 (chars up to 127, booleans) share one box per value (`boxCache`), as `Integer.valueOf` does, so `Integer a = 127, b = 127; a == b` is true and 128 isn't. Unboxing null throws the JDK's NullPointerException (`Cannot invoke "java.lang.Integer.intValue()" because "n" is null`).
  - **NullPointerException messages** name a method as the JVM does (`methodText`): the receiver's static class and the erased parameter types, `String` and `Object` without their package (`"Main$Node.link(Main$Node, int)"`, `"java.util.List.size()"`, `"String.length()"`), and an array by its static element type (`Cannot store to int array`, `object array`, `byte/boolean array`).
- **Java steps follow pythontutor.com (#24)** — a step shows the state *before* its line runs (`stepAt`). There is one before each statement; one at each loop test (a `for` shows its variable after the update, before the test; a for-each's first step comes before its variable exists, and each later one shows the previous element; a do-while steps at its `while` line); one entering a method or constructor, at its declaration line with the parameters (and `this`) bound, before its first line (not for main); one as it returns, at the `return` (or a void method's closing brace), showing the value as a variable named `return ↵` (`RETURN_VALUE`, as the Python engine shows it); one where an exception is raised; and main's return, at its closing brace, is the last step, the final state. As CPython emits no new line event while a frame stays on one line, a statement on the line its frame last stepped at takes no step (`lastStepLine`): `if (n < 2) return n;` and `a(); b();` are one step each. A loop's next test (a backward jump), a return and a method's entry are always steps (`force`). A step shows at most 100 frames (`MAX_SHOWN_FRAMES`): main, a `… n more frames` note, and the deepest 98.
- **Java multiple top-level classes**: a single source may declare more than one top-level class (e.g. a `Tester` class alongside the `Logic` class it exercises — the standard CS1/CS2 tester+logic split). The binder declares every class, and the entry class is the first one declaring `static void main(String[])` (`BProgram.entry`); stack traces name the file after it (`Main.java`). Names resolve through the binder's scopes, so an unqualified call in a non-entry class finds its own class's methods, and `ClassName.method()` reaches a user class before a library one (a user `class Math {}` shadows the built-in). `javac` forbids two *public* top-level classes per file, but this educational engine is intentionally lenient.
- **Java standard library (`src/engines/java/stdlib/`)**: a broad emulated subset for CS1/CS2 coursework, implemented as pure functions over a small `StdlibContext` (heap + alloc + `random()` + `stdin`) so it lives outside the evaluator. The binder resolves a name to a user class first (a user `class Stack {}` shadows the built-in), and the evaluator hands library calls to the stdlib: `callStaticMethod` (plus `getStaticField` for constants like `Math.PI` / `Integer.MAX_VALUE`, in `libraryStatic`), `newBuiltin` (in `newLibrary`), and `callInstanceMethod` (in `instanceCall`). Coverage: extended `Math`; wrappers `Integer/Long/Short/Byte/Double/Float/Boolean/Character` (parse/valueOf/radix strings/constants/compare); `Arrays` (toString, sort, fill, copyOf/Range, equals, binarySearch, asList); `Objects`; `System` (`currentTimeMillis`, `nanoTime`, `arraycopy`, `exit` → `HaltSignal`, caught in `execute()`); `String.format` + `System.out.printf` (shared `javaFormat`); `Collections` and `List/Set/Map.of`; the collections `ArrayList/LinkedList/Vector/Stack/ArrayDeque/HashSet/LinkedHashSet/TreeSet/HashMap/LinkedHashMap/TreeMap/PriorityQueue`; `Scanner` (real tokenization over `stdin`, incl. the `nextInt`→`nextLine` gotcha); and `Random` (Java's 48-bit LCG, so seeded sequences match `java.util.Random`). `String`, `StringBuilder`/`StringBuffer` and boxed values' methods live in `stdlib/strings.ts` (see the strings note). **Comparators**: `compareWith(cmp, a, b)` in `util.ts` orders by a user object's `compare()` (through `invokeUserMethod`) or a library comparator, which is a `Comparator` heap object with a hidden `__order__` field (`Collections.reverseOrder()`, `Comparator.naturalOrder()`/`reverseOrder()`, `String.CASE_INSENSITIVE_ORDER`, `reversed()`). `Collections.sort`/`max`/`min`, `List.sort` and `Arrays.sort` take one. A `PriorityQueue`/`TreeSet`/`TreeMap` built with one keeps it in `__cmp__`, and a `TreeSet`/`TreeMap` with a comparator treats elements that compare as 0 as equal. Natural ordering of an object with no `compareTo` throws ClassCastException, as Java does. Map copy constructors (`new HashMap<>(other)`) copy the entries. How the collections behave is in the next note. **Functions (#16, `stdlib/functional.ts`)**: `applyFunction(fn, method, args)` calls a function value: a library comparator, a library function object (`Function`, `Predicate` or `Consumer` with a drawn `kind`: `Function.identity()`, `f.andThen(g)`, `f.compose(g)`, `p.and/or/negate`, `Predicate.not`/`isEqual`, `BinaryOperator.minBy/maxBy`), else the program's code (a lambda or an object, through `invokeUserMethod`; null is a NullPointerException). `functionalMethod` gives any function value the default methods (`reversed`, `thenComparing` with the overload chosen by the argument's `functionShape`, `andThen`, …); library comparators gain the orders `comparing`/`comparingInt`/`comparingDouble`/`comparingLong` (with a `key` and optional `keyComparator`) and `then`, and `Map.Entry.comparingByKey/Value`. The collections' functional methods (`collectionFunctional` in `collections.ts`): `forEach`, `removeIf` (every element tested first, then removed through the iterator), `replaceAll`, and a map's `forEach`, `computeIfAbsent`, `computeIfPresent`, `compute`, `merge`, `replaceAll`, all through the collection's own methods (so immutable ones refuse). `Optional`/`OptionalInt`/`OptionalDouble` are library objects drawn with their `value`. **Streams (#16, `stdlib/streams.ts`)** are lazy: a stream object (drawn with its `source` and `pipeline` text) holds a source read when a terminal operation runs and a list of stages (JS generators); the terminal operation pulls each element through every stage before the next, so side effects interleave as in Java, `anyMatch`/`findFirst`/`limit` stop early, and an infinite `Stream.iterate` works with `limit`; a stream used twice is an IllegalStateException. Sources: a collection's `stream()`, `Arrays.stream`, `Stream.of/empty/iterate/generate`, `IntStream.range/rangeClosed/of/iterate`, `String.chars()`/`lines()`. Stages: `filter`, `map`, `mapToInt`, `mapToObj`, `mapToDouble`, `asDoubleStream`, `boxed`, `flatMap`, `distinct`, `sorted`, `peek`, `limit`, `skip`. Terminal: `forEach`, `count`, `sum`, `average`, `min`, `max`, `reduce`, `collect`, `toList`, `toArray`, `anyMatch`/`allMatch`/`noneMatch`, `findFirst`/`findAny`. Collectors: `toList`, `toSet`, `joining`, `counting`, `summingInt`, `averagingInt`, `groupingBy` (with a downstream collector), `toMap` (duplicate keys are Java's IllegalStateException).
- **Java collections (#21, `stdlib/collections.ts`, `stdlib/hashing.ts`)**:
  - **Storage, in iteration order.** Lists, sets and queues keep their elements in a `__data__` array, maps their keys and values in parallel `__keys__`/`__values__` arrays, always in the order Java iterates them, so printing, drawing and for-each just read them: lists by index, an ArrayDeque head to tail, a PriorityQueue as its binary heap (sift-up/sift-down and heapify as the JDK does, so `[1, 2, 4, 5, 3]` prints as in Java), a HashSet/HashMap bucket by bucket, the linked variants in insertion order (or access order, `new LinkedHashMap<>(n, f, true)`), a TreeSet/TreeMap sorted (binary search, comparing the key first as TreeMap does; a tree's first key is compared with itself, so an unorderable one fails at once; null with natural ordering is a NullPointerException).
  - **HashMap's table (`hashing.ts`).** `hashCodeOf` is Java's hashCode for every value: String's, the boxes' (a char is a Character, a long a Long), a user `hashCode()`, the collections' (List: 31·h + e, Set: the sum, Map: the sum of key ^ value) and otherwise the identity hash (`identityHashCode`, the hex an object prints). A key's hash is spread (`h ^ (h >>> 16)`) and kept in the table (`LibraryState.table.hashes`, parallel to the keys), so a key whose hashCode changes isn't found again, as in Java. `hashInsert` puts a new key at the end of its bucket and doubles the table past 0.75 of its capacity, or when a bucket reaches 9 keys in a table smaller than 64 (treeifyBin); doubling stably re-sorts by the new bucket. `presize` sizes it as `putMapEntries` does for `new HashMap<>(map)` and `putAll`, and `new HashSet<>(c)` asks for `ceil(max(c.size(), 12) / 0.75)` (JDK 19+). Lookups need the same hash and `key.equals(k)`. Equality (`valuesEqual`/`javaEquals`) is Java's: boxes of different types differ (a map with the key 'a' doesn't contain 97), lists compare by elements in order, sets and maps by contents, entries by key and value. Tree bins (9+ colliding keys in a table of 64+) aren't modeled.
  - **State that isn't drawn** is the object's `state` (`LibraryState` in `types.ts`): `modCount`, the hash `table`, a `restriction` (`immutable` for List.of/Set.of/Map.of/copyOf, `Collections.empty*`/`singleton*`/`nCopies` and unmodifiable views; `fixedSize` for Arrays.asList), `accessOrder`, and `snapshotOf`. `callInstanceMethod` refuses every method in `MUTATORS` for an immutable collection with UnsupportedOperationException; a fixed-size list allows `set` and `sort` but refuses changes of size (`remove(Object)` only when it would remove something, as Java does).
  - **Views.** keySet() and values() are `KeySet`/`Values` objects whose `__data__` is the map's own `__keys__`/`__values__` array, so they are always current; removing through them removes from the map. entrySet() is an `EntrySet` of `MapEntry` objects, refreshed from the map whenever it is used (keeping the entry objects of keys still there); an entry's `__map__` makes `setValue` write through, and `getValue` reads the map's current value. subList() is a `SubList` with `__target__`, `__offset__` and `__size__` that reads and writes its parent's range (`clear()` removes the range) and throws ConcurrentModificationException once the parent changed size otherwise. An unmodifiable view refers to its collection as `__unmodifiable__`: reads go there (`collectionElements`/`mapContents` in `types.ts` follow it), changes are refused. Arrays.asList(array) uses the array itself as `__data__`, so each writes through to the other. headSet/tailSet/subSet, headMap/tailMap/subMap and the descending views are copies marked `snapshotOf`; changing one is an error ("isn't supported in JavaTutor yet"), not a silent miss. `rootOf` follows views to the collection that holds the data.
  - **Iterators fail fast.** Structural changes count `modCount` (`modified`); an iterator (an `Iterator` object, with `collection` and `cursor` drawn and its `IterationState` in `state`, or the JS-side one `forEachIterator` gives the evaluator's for-each loop) remembers the count and throws ConcurrentModificationException from `next()` if it changed. `hasNext()` is decided as each class does (`iterationStyle`): `cursor != size` for ArrayList/Vector/subList (so removing the second-to-last element ends a for-each quietly), `cursor < size` for LinkedList/ArrayDeque/PriorityQueue, and "found a next entry when it moved" for hash and tree maps and sets. `Iterator.remove()` removes what `next()` returned (IllegalStateException otherwise); a PriorityQueue iterator keeps an element `removeAt` moved behind the cursor for later (`forgetMeNot`), as the JDK does; `descendingIterator()` walks from the end.
  - **Messages.** Index errors carry each class's message: ArrayList `Index 5 out of bounds for length 2` (and `Index: 3, Size: 2` for add), LinkedList `Index: 4, Size: 2`, Vector/Stack ArrayIndexOutOfBoundsException `Array index out of range: 2`, Arrays.asList/List.of ArrayIndexOutOfBoundsException; Stack.pop/peek on empty is EmptyStackException, Queue.remove/element and getFirst on empty NoSuchElementException, ArrayDeque and PriorityQueue refuse null, Set.of/Map.of duplicates are `duplicate element: x` / `duplicate key: k`.
  - **Printing.** The evaluator's `stringify` prints elements with their own `toString()` (a collection holding itself prints `(this Collection)` / `(this Map)`, an entry `k=v`), and so do a collection's `toString()`, `Arrays.toString` and `Arrays.deepToString` (through `StdlibContext.stringify`). A user class without `equals`/`hashCode`/`toString` gets Object's (`objectMethod`: identity, the identity hash, `Main$P@1b6d3586`).
- **Java library objects, drawn**: `serializeObject` renders collections inline with `list`/`set`/`map` objectTypes, reading them through `mapContents`/`collectionElements` (so views and unmodifiable collections show what they show; the reachability walk never reaches the backing arrays, and they aren't drawn; `KeySet`/`EntrySet` are sets, `Values`/`SubList` lists), draws a `Scanner` as the input it has left (`remaining`, a String from `scannerRemaining`, whose display shows its escapes), and hides internal `__`-prefixed fields on other library objects. Library objects whose state matters keep it in visible fields: an `Iterator` has `collection` and `cursor` (it walks the live collection), a `Random` its 48-bit `seed` (a long, exact in a double), and a library `Comparator` its `order` and, for `reversed()`, `base`; `javaValueToString` (in `types.ts`) formats collections (`[a, b, c]`), maps (`{k=v}`), `Map.Entry` (`k=v`), and `StringBuilder` (its text). `for (x : coll)` works over any collection through `forEachIterator` (see the collections note). **Library objects are tagged, not recognized by name (#8):** everything the stdlib allocates (`ctx.allocObject`), plus `StringBuilder` and `new Object()`, is a `JavaObject` with `builtin: true` (`isBuiltinObject`). Drawing, printing (`stringify`, `javaValueToString`), method dispatch (`instanceCall` → `callInstanceMethod` / `stringBuilderMethod`), for-each, `instanceof` (the library hierarchy) and comparator detection all check that tag. So a student's `LinkedList`, `Stack` or `HashMap` class is an ordinary object showing every declared field (even `__`-prefixed ones), and runs its own methods.
- **What a Java step shows (#9)** — `recordStep` builds each snapshot from the evaluator's state:
  - **Static fields.** When the program declares any static field, the first frame is `STATIC_FIELDS_FRAME` ("Static fields"), like the JS and Python global frame, and it is there from the first step, so frame indices don't shift mid-run. It lists `Class.field` for every class whose `state` (`ClassRuntime`) isn't `'pending'`: a class's statics appear once it starts initializing (lazily, at first use), with its initializers' values.
  - **Reachability.** `reachableHeap` walks from the frames' variables, each frame's `thisArg` and the static fields. It follows the properties each object is drawn with, so its edges match the drawing exactly, and returns the objects sorted by id (creation order). Unreachable objects stay in `this.heap`, since JS temporaries in the middle of an expression can still hold them; they just aren't drawn. An exception in flight isn't a root (as in the other engines); a caught one is drawn through its catch parameter.
  - **`this`** goes in the frame's `thisArg` (the UI's "this" section), not in its variables (`visibleVariables`).
  - **Unassigned locals.** A local declared without an initializer gets a slot with `unassigned: true` (`declare` without a value), so names still resolve to it, but it isn't drawn. The first write clears the flag (`slotReference`'s `set`); a read before that throws `notInitialized` (javac's "might not have been initialized"). That never fires for a program javac accepts, since definite assignment guarantees a write on every path, and #23's flow analysis rejects the others before running. `var x;` is javac's error, from the binder.
  - **Scopes.** Loops, labeled statements, `switch` and try/catch/finally restore the frame's scope when they catch a break, continue, return or exception, so no stale block frame survives, and a returning frame shows only its method's own variables. Blocks are labeled by construct: `for`, `while`, `do-while`, `if`/`else`, `switch`, `try`, `catch`, `finally`, `synchronized`, `static` (static initializer blocks). `blockIn`, `blockScoped`, `switch_` and `instanceInit` call `atFailureSite` before their `finally` restores the scope, so the step where a runtime exception starts still shows the block it started in.
- **What a Python step shows (#38)** — every variable the program has, in pythontutor.com's order (checked in its v5 source, `pg_logger.py`): a function's as its `f_locals` has them (the parameters, then the other locals in `co_varnames` order), the module's in the order they first appeared (`_module_order`: a variable deleted and defined again keeps its place), a class body's in the order it defined them (`_shown_names`). Hidden are only the names Python keeps itself: `_MODULE_BOOKKEEPING` (`__name__`, `__builtins__`, a docstring's `__doc__`, `__annotations__`, `__warningregistry__`, …), `_CLASS_BOOKKEEPING` (`__module__`, `__qualname__`, `__doc__`, `__dict__`, `__weakref__`, `__annotations__`, `__classcell__`, …), a method's `__class__` cell, and what a class body's namespace started with while it holds the same object (an Enum's `_generate_next_value_` from its metaclass's `__prepare__`, `frame_info["base"]`). So a class body shows `__init__`, `__repr__` and `__slots__`, and a program's `__version__` shows. A frame's kind (`_frame_kind`: module, function, class body) is kept on `_call_stack`. On the heap: a class is a `class` object (`_is_program_class`: its `__module__` is `__main__`) labeled with its bases (`Square(Rect)`), showing its class attributes and the methods the program wrote (`_class_attribute_shown`: a function, or a staticmethod, classmethod or property's function, only if its code is in `main.py`, so a dataclass's generated `__init__` and `total_ordering`'s `__gt__` aren't; a library's descriptor, a slot or a named tuple's getter, isn't; any other attribute only if it is a word of the source, `_source_words`, so an Enum's `_member_map_`, an ABC's `_abc_impl` and an eq-only class's `__hash__ = None` aren't); a library's class is drawn by its name only. A staticmethod, classmethod or property is a `function` object labeled `@staticmethod fee`, `@classmethod opened`, `@property balance` (HeapView adds no `()` to a property). A module is one `module` object labeled with its name, never expanded (pythontutor.com draws one the same way), which HeapView shows with no body (`HeapTypeDisplay.empty: null`). An Enum member is labeled `Color.RED` with its `value`. An object shows its `__dict__` and slots, a private name only when the program names it (`_instance_attribute_shown`: `self._balance`, the mangled `_Account__pin` for `self.__pin`, not an Enum member's `_value_` or a library's internals). Class names are read through `type`'s own descriptors (`_type_name`, `_type_dict`, `_type_bases`, `_type_mro`), so a metaclass's `__getattribute__` doesn't run; a class body's namespace that isn't a dict (a metaclass's `__prepare__`) isn't read.
- **Python values show as Python writes them (#37)** — the tracer gives each value its `display`, the text Python writes for it: `None`, `True`, `False`, a float's `repr` (`5.0`, `-0.0`, `1e+16`, `1e-07`, `inf`, `nan`; `value` the JSON number, or `"Infinity"`/`"NaN"`), an int past 2^53 (its digits, as `value` too, since a JSON number would lose them; past the digit limit `<int with N digits>`), and a complex number (type `number`, `(3+4j)`). Ints JavaScript holds exactly and strings have none (JS renders those the same; strings keep their double quotes, as pythontutor.com shows them). Python reference mode (`promoteToHeap`) names a value's type (`int`, `float`, `complex`) and labels it from that text, one object per text (5 and 5.0 are two); HeapView draws a `complex` object as it draws the other primitives.
- **Values show as Java writes them (#17)** — a `PrimitiveValue` may carry `display`, the text to show instead of rendering `value` by `type`. Both `ValueDisplay` components (FramesView, HeapView) and `scripts/java-viz.ts` go through `primitiveText()` (`src/utils/valueDisplay.ts`), which uses `display` when present, so the JS and Python engines (which never set it) render as before. `diffSnapshots` compares it too. The Java engine sets it in `javaToRuntime`: a char as a char literal (`'B'`, `'\t'`, and the default `'\u0000'`, via `charLiteral`), so it no longer looks like the String `"B"`; a String as a string literal with its escapes (`"a\nb"`, `stringLiteral`), which also makes the line break a Scanner has left visible; a double as `Double.toString` prints it (`5.0`, `1.0E7`); a float as `Float.toString` prints it. ints, booleans and longs need none. Exported viewer files store snapshots, and `display` is optional, so `CURRENT_EXAMPLE_SCHEMA_VERSION` didn't change.
- **Strings (#20, `stdlib/strings.ts`, `stdlib/regex.ts`)** — `instanceCall` sends a String receiver to `stringMethod`, a library StringBuilder to `stringBuilderMethod`, and a primitive (a boxed `Integer`, `Double`, …) to `boxedMethod`; `new String(…)` goes to `newString`.
  - **Identity.** `==` on strings compares identity, as in Java (`sameString`): a string made at run time (`javaString`: concatenation, Scanner input, `new String`, library results) is its own object, tracked in a `WeakSet`, while literals and text blocks are interned (`internedString`), and so is `intern()`'s result. javac folds constant expressions, and so does the binder (`BConst`, interned by `constValue`), constant variables included: `"h" + "i" == "hi"`, and so is `A + "i"` for `final String A = "h"`. A method that leaves a string unchanged returns it (`trim()`, `toLowerCase()`, `substring(0)`, `concat("")`, `replace` without a match, `String.valueOf(s)`), as Java returns `this`. `equals`, `switch` and the collections still compare characters.
  - **String methods** follow Java: `compareTo`/`compareToIgnoreCase` return the char or length difference, `charAt`/`substring`/`codePointAt` throw `StringIndexOutOfBoundsException` with JDK 21's messages, `equals` is true only for a String, `hashCode` is Java's, `replace("", x)` inserts between chars, `repeat` checks its count, and `chars()`/`codePoints()`/`lines()` are streams (#16).
  - **Regexes.** `javaRegex` translates a Java regex to a `RegExp`: leading `(?i)`/`(?s)`/`(?m)`, `\Q…\E`, `\A`/`\Z`/`\z`, `\h`, and POSIX `\p{Alpha}`-style classes. It rejects possessive quantifiers, atomic groups, class intersections, inner inline flags and other `\p{…}` with `UnsupportedFeatureError`; an invalid pattern is a `PatternSyntaxException`. `javaSplit` is `Pattern.split` step for step. `javaReplacement` applies Java's `$n`/`${name}`/`\x` rules (and its "Illegal group reference").
  - **StringBuilder**: `append` (a `char[]`'s chars, anything else through `stringify`, plus the 3-argument forms), `insert`, `delete`, `deleteCharAt`, `replace`, `setCharAt`, `indexOf`, `lastIndexOf`, `reverse`, `setLength`, `substring`, `charAt`, `length`, `isEmpty`, `compareTo`, and `equals`/`hashCode` by identity, with bounds checks.
  - **Boxed values** are their primitives, so `boxedMethod` gives them the wrappers' `xxxValue()`, `compareTo` (Integer/Long -1/0/1; Character/Short/Byte the difference; Double/Float via `compareFloating`), `equals` (only the same wrapper class: `Integer.equals(5L)` is false), `hashCode` (`boxedHashCode`, also for the static `Double.hashCode` and friends) and `toString`. `==` on boxes compares identity, with the `Integer` cache (see the evaluator note).
- **Java output model**: the interpreter accumulates a single `stdoutBuffer` string (`print`/`println`/`printf` all append; `println` adds `\n`); `snapshotStdout()` splits it into display lines, dropping one trailing newline. This fixes the older array-based model where a `print`/`printf` after a `println` glued onto the previous line. **stderr (#22):** `System.err` and `printStackTrace()` write through `appendStderr`, never into `stdoutBuffer`, so `snapshot.stdout` (and the JDK comparison) holds only stdout. Both streams also go to `consoleLines` (`writeConsole`: a line belongs to the stream that wrote its first characters), and once stderr has been used each step carries `console` (`snapshotConsole`: finished lines shared between steps, the open one copied). `printStackTrace()` (`stackTraceText`) prints the exception, the frames recorded in `exceptionTraces` (by heap id) when it was created (`new` of a Throwable, or `toExceptionValue` with the runtime's failure site), and its causes as `Caused by: …` with frames shared with the enclosing trace shortened to `... n more`, as Java does.
- **Java assignments go through the reference model (`references.ts`, #5)** — the evaluator evaluates an assignment target's parts (the object, the array and index) and turns the target (`BLValue`) into a `Reference` { `get`, `set`, `declaredType` } (`refPure`, `refGen`): a local or static slot (`slotReference`), an instance field (`fieldReference`) or an array element (`arrayElementReference`). `=`, every compound operator and prefix/postfix `++`/`--` all use it, so `a.next.next = v`, `this.data[this.size] = v`, `people[1].age = 31` and `counts[i]++` write exactly the variable named in the source.
  - An undeclared name is javac's `cannot find symbol`, before any step; there are no implicit locals.
  - Null and bounds checks run when a reference is *accessed*, which gives JLS order. `a[i] = e` evaluates `a`, `i`, then `e`, then checks, so the right-hand side runs before an `ArrayIndexOutOfBoundsException`. Compound assignment reads the variable first (JLS §15.26.2), so it checks before evaluating the right-hand side, and `x += (x = 5)` uses the old `x`.
  - Compound assignment and `++`/`--` narrow the result back to the variable's type (`compound`, `incDec`, through `castPrimitive`; a boxed variable is unboxed and boxed again), so `salary *= 1.5` stays an int and `c += 2` stays a char.
  - A field access, method call or array access on `null` throws a catchable `NullPointerException` (a `JavaRuntimeError`). Its message names the null expression the way Java's helpful NPE messages do, e.g. `Cannot read field "val" because "n.next" is null`. Array writes are bounds-checked with Java's message.
  - The RHS is evaluated once, which keeps heap allocations connected to the variable or field that receives them.
- **Java numbers (#10, `numeric.ts`)** — values follow Java's representation: `int`, `short`, `byte` and `char` (its UTF-16 code unit) are JS numbers in their range, `long` is a `bigint` (so 64-bit arithmetic is exact), `float` is a number rounded with `Math.fround` after every operation, `double` a number. Every function returns a value already in range.
  - **Operators.** The evaluator's `binaryOp` hands two primitives (the binder has unboxed them) to `binaryOperation`, which applies binary numeric promotion (JLS §5.6) and then `arithmetic`, `shift`, `bitwise` or `compareNumbers`. So `'a' + 1` is the int 98, `5L * i` a long, and `&`, `\|`, `^` on booleans are booleans. Integer `/` and `%` by zero throw ArithmeticException; floating-point division gives Infinity or NaN. Shift distances keep 5 (int) or 6 (long) bits. java-parser puts `<<`, `>>`, `>>>` in a `shiftOperator` node of `<`/`>` tokens, which the AST turns back into operators. Operands javac would reject (`true + 1`, a shift of a double) are javac's error, from the binder, and arithmetic on a null box is a NullPointerException (unboxing). Unary `-`, `+`, `~` promote (`unaryOperation`); `++`/`--` (`stepped`) add in the promoted type and convert back, so a byte 127 becomes -128.
  - **Conversions.** `convertNumber` implements widening and narrowing (JLS §5.1.2–§5.1.3): floating point to int or long truncates and saturates (NaN is 0), byte/short/char keep the low bits of that int, a long narrows by its low bits, and a long converts to float with one rounding. Casts use `castPrimitive`; compound assignment narrows through it too. The binder makes every conversion an explicit `BConvert` node (widen, narrow, box, unbox, checkcast) wherever Java converts a value: assignment, arguments, returns, operands. So `double x = 1;` holds 1.0 (without it, `target / x` ran integer division: the Newton's-method √2013 regression), `long n = 5;` holds 5n, `int x = 'a';` holds 97, and a constant narrows (`byte b = 10;`). `assignmentConversion()` (in `references.ts`) still converts what a `Reference` stores.
  - **Literals** (`integerLiteralValue`, `floatingLiteralValue` in `literals.ts`): hex, octal and binary digits (using every bit: `0xFFFFFFFF` is -1), underscores, `L`, `f` and `d` suffixes. A value that doesn't fit is javac's error before any step (`integer number too large`, `floating-point number too large` or `too small`); the decimal 2147483648 is allowed because it can only follow a minus sign.
  - **Printing.** `floatToString` is Java's `Float.toString` (JDK 19+): of the decimals that round back to the float, the shortest, then the closest (ties to even), with two digits competing when one is enough (`Float.MIN_VALUE` is `1.4E-45`), from the float's exact decimal expansion. `doubleToString` is `Double.toString` by the same rule (#19); V8's shortest round-trip digits are already the closest, so only a one-digit result goes through the exact path (`Double.MIN_VALUE` is `4.9E-324`). Both match the JDK on every one of 20,000+ sampled values. `javaDecimalLayout` lays digits out Java's way (plain in [10⁻³, 10⁷), else `1.0E10`). A long prints its exact digits.
  - **Formatting (#19).** `javaFormat` (`stdlib/format.ts`) rounds `%f`, `%e` and `%g` half up from `shortestDouble`'s digits with BigInt arithmetic, as Java's Formatter does (`%.1f` of 0.15 is 0.2), writes `%e` exponents with at least two digits, and picks `%g`'s notation from the rounded magnitude. It handles the flags `- 0 + space , (`, NaN, Infinity and -0.0, and throws Java's `IllegalFormatConversionException` (`f != java.lang.Integer`), `MissingFormatArgumentException`, `UnknownFormatConversionException` and `IllegalFormatPrecisionException`. A lone `Object[]` argument is the arguments. `%s` renders through the `stringify` it is given (the interpreter's, via `StdlibContext.stringify`), so a user `toString()` is used; `String.valueOf` uses it too.
  - **Identity strings (#19).** An array prints as `Class.getName()@hash` (`arrayClassName`: `[I`, `[[D`, `[LMain$Pt;`) and a user object without `toString()` as `Main$Pt@hash`, a library one as `java.lang.Object@hash`. The hash (`identityHash`) depends only on the heap id: eight hex digits, the same every run. `print`/`println`, `String.valueOf` and `StringBuilder.append` print a `char[]`'s characters (`charArrayText`).
  - **Display (#17).** `javaToRuntime` gives each char, float, double and String Java's own rendering in the value's `display` (see the display note below), and sends a long as `{ type: 'bigint', value: '<digits>' }` (exact past 2^53).
  - **Library.** `Math.abs`, `max`, `min`, `floorDiv` and `floorMod` keep the promoted type; `Math.round(double)` is a long and `Math.round(float)` an int; `Math.rint` rounds half to even. `Integer`/`Long`/`Short`/`Byte` `parse*` and `valueOf` use `parseIntegerText`, with Java's NumberFormatException messages (no trimming; `Value out of range` for Short and Byte). `Long.MAX_VALUE` and friends are exact; `Float` statics are floats; `Double.compare` orders NaN and -0.0 as Java does. `String.format` prints a long's `%d` exactly, and `%x`/`%o` as wide as the value's type. `Scanner.nextInt` (and `nextLong`, …) throws InputMismatchException and leaves a bad token unread; `nextLong` returns a long; `Random.nextLong` is exact and `nextFloat` a float. `System.currentTimeMillis` is a long. `Arrays.fill` converts to the element type, and `Arrays.copyOf` pads with the element type's default.
- **Java classes, statics and initialization (#6)** — the binder builds a `ClassSymbol` per class or interface (`outer` for a nested one, `isInner` for a non-static nested one, `superclass`: a program's class, Object or a library exception class, `interfaces`) and a `BClass` with two initializer lists in textual order: `staticInit` (static field initializers and `static {}` blocks) and `instanceInit` (instance field initializers and `{}` blocks). The evaluator keeps a `ClassRuntime` per class: its initialization `state` and its static slots.
  - **Statics are per class** (`ClassRuntime.statics`), so same-named statics in two classes don't collide. Interface fields are static constants of the interface.
  - **Class initialization is lazy** (JLS §12.4): `initClass` runs a class's `staticInit` once, at its first `new`, static method call or static field access, in a `<clinit>` frame. The entry class is initialized before `main`. A class being initialized isn't re-entered, so a static read during its own initialization sees the default value. An exception from a static initializer becomes `ExceptionInInitializerError`, and later uses throw `NoClassDefFoundError`.
  - **Constants don't trigger initialization:** a *constant variable* (a `final` primitive or String static whose initializer is a constant expression, `FieldSymbol.constant`) is set by `initConstants()` before the program starts, and reading it doesn't initialize its class (javac inlines it). An assignment to a static field evaluates its right-hand side first, so `C.x = f()` runs `f()` before initializing `C`, as the bytecode does (putstatic comes last); reading one, or a compound assignment, initializes first.
  - **Objects:** `new` initializes the class before evaluating arguments, allocates the object with default field values, then runs `construct` with the constructor the binder chose by argument types. A constructor either delegates with `this(…)` (another frame, which runs the initializers) or calls its superclass's constructor (`superCall`: a program's class runs its constructor in a frame of its own; a library exception's `superConstructor` records the message and cause from `super(msg)`, `super(msg, cause)` or `super(cause)`) and then `instanceInit`, before its body (JLS §12.5). A class with no constructor gets the default one, which runs the implicit `super()` and `instanceInit`, in a frame only if one of them runs code. Initializers run in the constructor's frame with a scope holding only `this`, so they can't see its parameters or the caller's locals.
  - **`instanceof`, casts and `catch`** use `instanceOf` and `isSubclass`: a user class, its superclasses and its interfaces (transitively), then the library's own hierarchy (`stdlib/hierarchy.ts`: collections, exceptions, `String`/`CharSequence`, boxed primitives as `Integer`/`Number`, arrays as `Object`/`Cloneable`). A reference cast to a type JavaTutor knows is checked (`ClassCastException`); a cast to a type variable isn't, as in Java. Exceptions print with Java's names: `Main$MyException` for a nested user class, `java.lang.IllegalStateException` for a library one (`binaryName`).
  - **Varargs:** the binder packs a variable-arity call's trailing arguments into a new array, unless one array is passed. `main`'s `String[] args` is bound to an empty array only when main's body mentions it (`mentionsLocal`), so other programs' steps don't show it.
- **Java statements and unsupported constructs (#6)** — every statement and expression node either runs or throws. Nothing falls through to `null` or is silently skipped.
  - **Labels:** labeled statements pass their labels to loops (`targets()` matches `break label`/`continue label`), and a labeled statement catches a `break` naming it.
  - **Switch:** `switch_` handles statements and expressions: arrow rules (no fall-through; expression, block or throw), colon groups (fall-through until `break`, or `yield` in an expression), several labels per case, `default` anywhere (it applies only if no label matches), `case null`, and type patterns with `when` guards. A null selector without `case null` throws NPE. The switch block is one scope (labelled "switch").
  - **try:** `tryStmt` runs plain try and, through `withResources`, try-with-resources, which opens resources in order in a scope visible only to the try block, closes the opened ones in reverse, and suppresses a close exception when another is propagating. `System.exit` (`HaltSignal`) skips catch and finally, as in Java, and so does an engine error such as an `UnsupportedFeatureError` or the step limit. Only Java exceptions (`exceptionClassOf`, which doesn't allocate) are catchable.
  - **Patterns:** an `if` whose condition has an `instanceof` pattern evaluates it in a scope of its own (labelled "if"), so the variable is visible in the branches and gone after. It is copied to the enclosing scope for `if (!(o instanceof T t)) return;`, JLS flow scoping, approximated by `canCompleteNormally`. Elsewhere a pattern binds in the current scope.
  - **Other statements:** `synchronized` runs its block after a null check. `assert` takes a step but isn't evaluated, since `java` runs without `-ea`. `yield` is a `YieldSignal`.
  - **Unsupported constructs** throw `UnsupportedFeatureError(construct, line)` with messages like `Line 5: Lambda expressions aren't supported in JavaTutor yet`: extending a collection or other library class (except the exceptions), an anonymous subclass of one, annotation types, `X.super.m()`, record patterns (their variables are declared, so the code using them binds), a lambda passed to a library method the stubs lack, library classes the stdlib lacks (`new Thread()`), hex float literals. Declarations are rejected by the binder, before any step. Expressions and statements are `Unsupported` nodes, rejected when evaluated, so earlier steps remain.
- **Java failures (#7)** — `execute()` returns `ExecuteResult`: `snapshots`, a one-line `error` summary (what tests and the harness read), and `failure` (the `RunError` the worker sends).
  - **Frame lines.** Every `Frame` records its `kind` (method, constructor, `<clinit>`) and the `line` it is executing. `stepAt` sets it, so a caller's line stays at the call site while its callee runs.
  - **`atFailureSite(e)`.** `drive` calls it whenever a frame ends by throwing, and so do blocks, switch, try and `endedBy`. The first time a failure passes, while its frames are still on the stack, it records the line and a Java stack trace (`Main$Point.<init>(Main.java:6)`, at most 64 frames) in `failureSites`. For a runtime exception (`/ by zero`, a null field, a library error) it also records a step at the throwing line, unless the last step already shows that line with the same frames (`lastStepShows`), so a caught one shows the throwing method's frame before the catch. A `throw` statement has already recorded its own step (again after the exception's constructor ran, if it took steps). Engine errors get no extra step, because the program never really got there, and compile-error cases stay stepless.
  - **Uncaught exceptions** are summarized as `Exception in thread "main" java.lang.ArithmeticException: / by zero` (user classes by binary name, `Main$Oops`, using their own `toString()` if they have one), with the trace in `failure.stderr`.
  - **Stack overflow.** Java frames don't use JavaScript's stack: a call past `maxDepth` frames throws a catchable `java.lang.StackOverflowError`, whose trace is cut to 64 frames and `... n more`. A JavaScript stack overflow (deep recursion inside library code) becomes one too (`isStackOverflow`, which avoids regular expressions, since compiling one at the stack limit can itself overflow).
  - **Standard-library errors.** A `StdlibError` from a library call is re-thrown with the call's line (`stdlib(line, call)`).
  - **Internal errors.** Any other JavaScript error becomes "Internal JavaTutor error (please report it)" for students. The summary keeps the JavaScript text, so the `js-errors` invariant still flags engine bugs.
  - **Limits** (`RunLimits`, lowerable in tests via `new JavaInterpreter(stdin, limits)` or `runJava(source, stdin, limits)`): 5000 steps (`maxSteps`), 1,000,000 units of work, counting steps recorded or not (`maxWork`, which also stops an endless loop inside `toString()`, replacing the old per-loop iteration cap), 8.5 seconds (`timeBudgetMs`), and 1200 Java frames (`maxDepth`, a StackOverflowError). The first three throw `ExecutionLimit`. It isn't a Java exception, so no catch or finally runs.
- **Java compile errors (#23)** — a program javac rejects never runs: the console lists its errors as javac does, and the editor marks each one's line.
  - **Flow analysis** (`semantic/flow.ts`, `checkFlow`, which the binder runs over the bound tree) tracks, per path, a `State`: the variables definitely assigned (`'dead'` where code can't run) and those possibly assigned; a condition splits it into its true and false states (`&&`, `||`, `!`, `?:`, constants, JLS ch. 16). It reports reachability (JLS §14.22: `unreachable statement`, once per block, after which analysis goes on; an `if` branch stays reachable whatever its condition, so `if (DEBUG) …` is fine, a constant condition only making the branch it skips vacuously assigned, `reachable`), `missing return statement` at the method's closing brace, `variable x might not have been initialized` (only for locals declared without an initializer in the code being analyzed, `ownLocals`, so a local class's methods see their captured locals assigned, and parameters, pattern and catch variables are always assigned), finals (`cannot assign a value to final variable x`, `final parameter x may not be assigned`, `variable x might already have been assigned`, `variable x might be assigned in loop`, a blank final field a constructor leaves unassigned, at its closing brace, or `not initialized in the default constructor`, and a blank static final the static initializers leave unassigned), checked exceptions (JLS §11.2: a `throw`, a call of a method or constructor with a `throws` clause, a try-with-resources `close()`, a rethrown catch parameter's precise types; instance initializers' exceptions go to the constructors, a lambda's to its function type): `unreported exception X; must be caught or declared to be thrown` at the call's `(`, `exception X is never thrown in body of corresponding try statement`, `exception X has already been caught`; `break outside switch or loop`, `continue outside of loop`, `undefined label: x`, and a lambda block that can end without returning its value.
  - **javac's order** (`javacOrder` in binder.ts): a `syntax` diagnostic (`not a statement`, which javac's parser reports for an expression statement that isn't an assignment, `++`/`--`, a call or `new`; at a binary operator) hides every other error; otherwise each top-level class in source order, its type errors in source order, then its flow errors, but only while no error has been found, as javac skips flow analysis once there are errors.
  - **javac's messages and carets**: `cannot find symbol` with its `symbol:` and `location:` lines (`class Main`, `variable s of type String`; none for a method missing from `this`), at a member's `.`; `bad operand types` at the operator; one method's argument mismatch simplified to `incompatible types: …` at the argument (`simplified`, so the listing ends with javac's note that messages were simplified); `cannot be applied to given types` with its `reason:` (`actual and formal argument lists differ in length`, `varargs mismatch; …`), at `new` for a constructor.
  - **Syntax errors** (`compileErrors.ts`): `describeParseError` gives java-parser's first error javac's message and caret by what java-parser expected and the rule it was in: `'X' expected` just after the previous token (`')' or ',' expected` in an argument list), `reached end of file while parsing`, `'else' without 'if'`, `class, interface, enum, or record expected` (also for an extra `}`, which empties java-parser's lexer mode stack), `<identifier> expected`, `invalid method declaration; return type required`, `not a statement`, `illegal start of statement`, `illegal start of expression`. First `lexicalError` scans the source for what javac's scanner reports: `unclosed string literal`, `unclosed character literal`, `empty character literal`, `illegal line end in character literal`, `unclosed text block`, `unclosed comment`, `illegal character: '#'` (`'“'` for a curly quote pasted from a document). Where javac's message depends on how its parser recovers (`if (x = = 1)`, a `,` instead of `;` in a for header, a method declared inside a method), JavaTutor's differs, but the line is right.
  - **The result.** `compileFailure` makes the `compile` RunError: `message` and `line` are the first error's, `lines` every error's line, and `stderr` javac's listing (`javacListing`: `Main.java:3: error: ';' expected`, the source line, a caret under the column keeping the line's tabs, the message's detail lines, then `1 error` / `N errors`, at most 100), named after the entry class (`javaFileName` for a syntax error: the public class, else the first). `runJava` returns a syntax error this way too. An `unsupported` diagnostic still comes first, alone, as an `error`. The listings match javac's byte for byte for every corpus compile-error case and every program in `compile-errors.test.ts`.
- **Java subset limits** — this is not a full JVM. Generics are type-checked by the binder and erased when the program runs. It does not currently support extending a library class other than an exception, record patterns, access control, file/network I/O, threads, or reflection (a `Class` object only has `getName`, `getSimpleName` and `toString`), and its streams are the subset listed in the stdlib note. These are rejected with `UnsupportedFeatureError`, not guessed at. Multiple top-level classes in one source **are** supported (see the multiple-top-level-classes note above), as are interfaces with constants and static methods. The standard library is an emulated subset (see the stdlib note above), not the real JDK — only the listed classes/methods exist: a method the real class doesn't have is javac's "cannot find symbol" before running, and one it has that the subset lacks throws `Unknown method` when called. Among the collections there is no `ListIterator`, a load factor other than 0.75 is ignored, `Set.of`/`Map.of` iterate in insertion order (the JDK's order is randomized per run), and the sub-range and descending views are copies (see the collections note).
- **Steps follow pythontutor.com in every engine (#24)** — a step shows the state *before* its line runs. The editor marks the step's line ▶ "About to execute" and the previous step's ✓ "Just executed"; on the last step of a run that ended normally, the final state, it marks only ✓ on the line that ran last (`stepMarkers` in `src/utils/stepMarkers.ts`). When each engine takes its snapshots:
  - **Python**: `sys.settrace` events. A `call` event is a step at the `def` line with the parameters bound; a `line` event comes before its line runs; a `return` event is a step showing `return ↵`; the module's return is the final state.
  - **Java**: see "Java steps follow pythontutor.com" above (entry at the declaration line, a step before each statement and loop test, return steps, main's closing brace last).
  - **JavaScript**: `instrumentBlock` puts a `__capture__` before each statement that runs (not before a function declaration, a block, `try` or a label; an `if` or a loop with a test steps through `__condition__`, a do-while at its `while`), and the program body ends with a final capture (`isFinal`), which the runtime puts on the line that ran last. A function's entry is the capture before its first statement (its parameters bound by `__pushFrame__`); `return e` steps with its value through `__popFrame__(e, line)`, and reaching the closing brace through `__popFrame__(undefined, endLine)`. `__condition__` refreshes the variables the test sees (`buildVarArgs`, as a capture does), and a `for (let …)` test shows its variables in a `for` frame of their own (`blockFrame`; the loop's frame is pushed in its body, for per-iteration bindings). As CPython reports a line once while a frame stays on it, `__capture__` takes no step on the line its frame last stepped at (`a(); b();`, a statement on its test's line), unless a frame was pushed or a loop iteration began since (`__framePushed__`, `__loopCount`). Synthetic statements (loop guards, frame pushes and pops) have no line and take no step. Frames are named as JavaScript names the function: its name, else the variable or class member it is defined as (a constructor by its class, `_inferredName`).
- **The JS console prints as Node does (#43)** — the decision on #43 was Node's `util.inspect` format (`[ 1, 2, 3 ]`, `{ a: 1 }`, `Map(1) { 1 => 'a' }`), what `node` prints and the goldens' own text. `src/engines/js/inspect.ts` holds `CONSOLE_SOURCE`, a script (a string, not a function's source: tsx and esbuild's keepNames would add helpers the worker lacks; no backticks or dollar-brace inside) that ports Node's lib/internal/util/inspect.js and console/constructor.js rule for rule: `formatValue`/`formatRaw` (brand checks through built-in getters, `getConstructorName` with `Function.prototype[Symbol.hasInstance]`, getPrefix, the tag left out when the class name already says it, `CountingMap` / `MapX`), `formatProperty` (`[Getter]`, unquoted identifier keys, `Symbol(s): v`, `[hidden]`), holes (`formatSpecialArray`), `groupArrayElements` (columns for 7+ short entries), `reduceToSingleString` (80 columns, at most three levels on a line), `strEscape` (single, then double, then backtick quotes), circular `<ref *1>`, depth 2, 100 items; `util.format`'s `%s %d %i %f %j %o %O %c %%`; and the console methods: `log`/`info`/`debug`/`dirxml` and `dir`, `count`, `table` (Node 24's left-aligned cells) and `time` to stdout, `warn`/`error`/`trace`/`assert` to stderr, `group` indenting by two. It never runs the program's code where Node wouldn't (getters, `toJSON`), and not even where Node would for a `Symbol.toStringTag` getter or a static `Symbol.hasInstance` (`tagOf`, `safeGet`); `%s`, `%d` and `%j` call a `toString`, `valueOf` or `toJSON` as Node does. What it can't know: a Promise's state (`Promise { <pending> }` unless `__promiseStates__` has it), a Map or Set iterator's items, and an error's stack frames: an error prints as Node lays it out with frames (`Error: msg`, `{\n  e: Error: msg\n}`), minus the frame lines (a sentinel `FRAME` line removed at the end); the suite drops frames from both sides too (`withoutStackFrames`). The runtime makes `self.console` `__makeConsole__(__write__)`: each call's text becomes lines in `__stdout__` (stdout's) and `__console__` (every line with its stream); a snapshot carries `stdout`, and `console` once stderr was used (`__outputOf__`), which ConsolePanel shows with stderr in red. `__runResult__` first adds a step (`__finishOutput__`) when output was written after the last step. Chrome's DevTools format the same values differently (`(3) [1, 2, 3]`, `{a: 1}`).
- **Every place code can appear is instrumented (#46)** — `instrumentStatement` handles every statement type (labeled statements as their loop or block, so a labeled loop has its guard and steps; `throw`, `with`, `switch`'s discriminant and tests, a catch parameter's defaults) and throws `UnsupportedSyntaxError` ("pipeline expression isn't supported in JSTutor yet") for one it doesn't know, which `prepareProgram` turns into an error before the program runs. `instrumentExpression` walks every expression and pattern through `EXPRESSION_CHILDREN`, the parts of each node type that can hold code, so it reaches functions in `new Promise(executor)`, member chains (`a.map(f).filter(g)`), after `!`/`void`/`await`, in sequences, tagged templates, computed keys and default values; a type missing from the table is an `UnsupportedSyntaxError` too. Loops instrument the code in their heads (a for's declarations, test and update, a for-of's source, a while's test) before wrapping their tests. `instrumentClass` instruments methods, field values, computed keys, the superclass expression and `static {}` blocks (`instrumentStaticBlock`: a frame named `<static_initializer>`, as V8's debugger names it, with `this` the class). `inferName` names anonymous functions and classes as JavaScript does: the variable, assignment target, property, default parameter or class field they are defined as.
- **The program doesn't see its instrumentation (#47)** — `instrument()` puts two lines before the program (`programFacts`): `__programLines__([...])`, the program's line for each line of the instrumented code (the line of the nearest step call at or before it, and each function's own line), and `__sourceTexts__({...})`, each function's own text (`functionTexts`: what Function.prototype.toString returns, the node's span, a method's from its key with `get`/`async`/`*` and without `static`), keyed by its instrumented text's length and hash (`sourceKey`, the same hash in the runtime's `__sourceKey__`); the two trees' functions are paired in order and the texts left out if they don't line up. The runtime replaces `Function.prototype.toString` to return a function's own text, and makes the runtime functions the program can reach (timers, `queueMicrotask`, `structuredClone`, the console's methods, `toString` itself) look native (`__looksNative__`); `structuredClone`'s DataCloneError quotes the function's own text (found by the quote's start, as the browser may shorten it). `__programLines__` finds where the program starts in the worker's script (V8's structured stack, read before `Error.prepareStackTrace` is put back, since V8 makes a stack when it is first read) and installs `__prepareStackTrace__`, so a stack is the header and the program's frames only, `at divide (main.js:2)` (`at main.js:12` at the top level); other browsers keep their own stacks. The heap drawing of an error reads no `stack` (V8 writes a stack's first line from the name at its first read, which a step before a constructor sets the name would freeze) and shows `message` and the error's own data properties. An uncaught exception's `stderr` is its stack.
- **JS values drawn as themselves (#48)** — the runtime's serializer gives NaN, Infinity, -Infinity and -0 a `display` (JSON has no such numbers, and `String(-0)` is `0`); draws an array's hole as `{ type: 'empty', display: 'empty' }` (`PrimitiveValue`'s `empty` type, grey in HeapView, `.value-empty`) and an accessor element as a placeholder, reading elements through their descriptors; draws an object's enumerable Symbol keys as `[Symbol(id)]`; and gives each Map entry a `keyValue` (`Property.keyValue`): the key drawn as a value, so an object key is a reference to its object (HeapView draws it with `ValueDisplay`, so it gets an arrow, and its "current" filter follows it; the runtime's `__collectHeap__` follows it; `key` is then `#<heapId>` for an object key, else the key's text). Snapshot sharing compares `keyValue` too, and values with `Object.is`, so a NaN is shared. `CURRENT_EXAMPLE_SCHEMA_VERSION` stays: an older viewer draws an `empty` value by its display text and ignores `keyValue`.
- **JS programs that don't parse (#50)** — Acorn still parses for instrumentation, but its words (`Unexpected token (7:31)`) aren't the browser's. `prepareProgram` returns Acorn's problem (`SyntaxProblem`: message, line, 0-based column), and `executeProgram` asks the engine itself (`ScriptChecker`): `checkScriptInWorker` loads the program as a worker's script, and a script that fails to parse fires the worker's error event with the engine's message and position (no browser gives a SyntaxError's line to eval or new Function; `syntaxProblemFromEvent` takes Chrome's `Uncaught SyntaxError: …` and Firefox's `SyntaxError: …`); a script that parses starts running, so after a second the worker is ended and Acorn's problem stands. `syntaxErrorReply` makes it a `compile` RunError with no steps, as JavaTutor's javac errors: `message` is `SyntaxError: <the engine's text>` (`missing ) after argument list`, `Unexpected end of input`, `Missing initializer in const declaration`), `line` and `lines` the engine's line, and `stderr` `Uncaught SyntaxError: …`, `    at main.js:7:31`, the line and a caret under the column (tabs kept). The banner says "Compile error", as for Java. The harness's `nodeCheckScript` compiles with Node's `vm.Script`, which gives V8's message and, in its stack, the line and a caret.
- **TDZ-aware instrumentation** — `let`/`const` tracked incrementally; `var`/`function` hoisted. A capture before a block's `let`/`const`/`class` declaration leaves its name out (`pending`), and so the outer variable it shadows.
- **Block scopes** — Loops with `let`/`const` use `isBlockScope` flag, rendered nested inside parent frame
- **Per-iteration bindings preserved** — `for (let i...)` keeps its init and update in the for-statement slots (not extracted into the parent block) so closures created inside the body capture distinct per-iteration values, matching ECMA-262 semantics
- **Frames leave with their code (#44)** — every function body is `var __fr__ = __pushFrame__(…); try { … } finally { __leave__(__fr__); }`, and every loop with a block frame keeps it as `const __bf__` and leaves it in a finally (`{ const __bf__ = __pushFrame__('while', …); try { while (…) { … } } finally { __leave__(__bf__); } }` around a while, do-while or for-with-extracted-init loop, the try inside the body of a for-in/for-of, whose frame is pushed per iteration). `__pushFrame__` returns its frame and `__leave__(frame)` takes it and every frame above it off the stack wherever it is (nothing when a return's `__popFrame__` already did), so a frame goes however its code is left: return, a throw, break, continue, a labeled break. A generator's or async function's frame leaves the stack at each `yield`/`await` and comes back when it resumes, on top of whatever runs then, as a debugger's call stack shows it: `suspendAtYieldAndAwait` rewrites `await x` to `__resume__(__fr__, await __suspend__(__fr__, x))` (the same for `yield`, `yield*`), and since a rejected await, `gen.throw()` and `gen.return()` re-enter the function in a catch or finally block, each of those inside it starts with `__resume__(__fr__)`; `__suspend__` splices the function's frames (its loops' included) off the stack into `frame.__saved`, `__resume__` pushes them back, and `__leave__` of a suspended frame just drops them. Nested functions keep their own frames. A `for await` loop's implicit awaits don't suspend the frame.
- **Derived class constructors** — instrumenter detects `extends` and skips reading `this` in the constructor's `__pushFrame__` call, avoiding a ReferenceError before `super()` returns
- **Getter/setter-safe serialization** — `__serializeHeapObject__` uses `Object.getOwnPropertyDescriptor` to detect accessor properties and renders them as `<getter>` / `<setter>` placeholders rather than invoking them (a getter that reads `this` would re-enter the runtime and recurse without bound)
- **Condition tracking** — `__condition__()` wraps if/else-if and loop tests, emits snapshots with `condition` field, after refreshing the variables the test sees
- **Value change animation** — `diffSnapshots.ts` compares consecutive snapshots, applies `value-changed` CSS class
- **Snapshot sharing (#18)** — `SnapshotSharer` (`src/utils/snapshotSharing.ts`) makes each snapshot reuse, from the steps before it, every frame, variable, heap object (by id, from its last version), property and stdout array that is structurally equal, and returns its input unchanged when nothing was replaced. Snapshots are never modified, so sharing equal data is always safe. The Java evaluator shares as it records each step (`recordStep` → `this.sharer.share`), so the worker's `postMessage` (a structured clone, which writes a shared object once) carries each unchanged object once: the insertion sort of 300 ints went from 75 MB to 2.3 MB, 1,000 objects in a list from 516 MB to 9 MB, the corpus from 51 MB to 4 MB. The granularity is a property: a changed object costs a new properties array of references, not its contents again. The store's `setSnapshots` also shares (cheap for steps already shared), which cuts what the Python steps keep in memory, though its worker still sends full snapshots. The JS runtime shares as it records too (#49): `__record__` passes each snapshot through `__shareSnapshot__` (`src/engines/js/sharer.ts`, the same algorithm as a script), so the insertion sort of 300 numbers posts 1.8 MB (26 MB before), recursion 1,000 deep 6.3 MB (52 MB), the runaway recursion stopped at the step cap 19 MB (208 MB, and 0.9 s instead of 8.5 s), and the whole Node corpus 33 MB as posted against 709 MB as JSON. JSON doesn't keep sharing, so an exported viewer file is as big as before. `scripts/java-payload.ts` and `scripts/js-payload.ts` measure all of this. The step cap stays at 5000, the same in all three engines.
- **Snapshot limit**: 5000 per execution. At the cap every engine stops the program and returns its steps with a `limit` error: the JS runtime throws `__STOP__` from `__capture__`, the Python tracer raises `_TutorStop` (a `BaseException`, so `except Exception` can't swallow it), and the Java interpreter throws `ExecutionLimit`. Java and Python also stop themselves after 8.5 seconds, so partial steps survive the worker's 10-second kill. That kill (the only case that loses the steps) remains for code that runs long without a trace event (a long computation inside one C call, `sum(range(10**10))`) or whose steps take too long to record (Python recursion hundreds deep, #39). A Python `while True: pass` does emit line events, and the step cap stops it.
- **Asynchronous JS (#45)** — the worker doesn't reply when the script's synchronous code ends: `WORKER_SOURCE` calls `self.__eventLoop__(done)` (an uncaught exception in the script still replies at once). The instrumenter ends the program with `__endScript__(line)` (the script's last step, the old final capture, `__scriptDone__` set) and adds `function __globals__()`, which reads every top-level name (each in a try, so one in its temporal dead zone is left out); every step taken inside a function refreshes the Global frame from it (`__refreshGlobals__`), so a callback changing a global shows at once. The runtime replaces `setTimeout`/`setInterval`/`clearTimeout`/`clearInterval` with timers in virtual time (`__timers__`, due = now + max(1, ms) as in Node, ordered by due time then by when they were set; an interval re-arms from its due time) and wraps `queueMicrotask`. `__eventLoop__` hops to a new task twice through a `MessageChannel` (`__hop__`: once for the microtasks, once for the browser's `unhandledrejection` task), then stops at the step cap (`__stopped__`, set when a capture throws `__STOP__`, which inside a promise only rejects it), the loop guard, a callback's uncaught exception (`__callbackError__`, `Uncaught …`), the first unhandled rejection (`unhandledrejection` listener, `Uncaught (in promise) …`), or the 8.5-second budget (`__TIME_LIMIT__`); otherwise it runs the next timer and repeats, and when nothing is left it takes a last step with the state after every callback (`__finalStep__`, at the line that ran last) and replies. The run ends at the first uncaught exception or unhandled rejection, as Node ends it (browsers would run the remaining callbacks; no corpus program prints after one). The step that starts a callback gets `label` (`ExecutionSnapshot.label`, shown next to "Frames" by `StepLabel` in VisualizationPanel): `setTimeout callback` / `setInterval callback` / `queueMicrotask callback` (set as the runtime calls it), `promise callback` (a frame pushed on a bare Global stack after the script, `__pushFrame__`) and `resumed after await` (`__resume__` on a bare stack); a callback's frame is alone under Global, as a debugger shows it. pythontutor.com's JS mode doesn't run async code at all.
- **Runs that end early (#7)**:
  - **JS:** the worker's reply comes from the runtime's `__runResult__(err?)` (after the event loop, #45): an uncaught throw is an `exception` (`TypeError: …`, stderr `Uncaught …`), and the loop guard or step cap is a `limit`. `throw` statements already have a pre-capture, so the last step is the throw.
  - **Python:** `run_traced` returns the steps plus an `exception` error with a Python-style traceback of the user's frames (`File "main.py", line N, in f`), for any exception the program raises (a `BaseException` such as `KeyboardInterrupt` included). A syntax error comes back as `{ type: 'error', line }`. The worker passes the source to `run_traced` as a str, never pasted into Python code (#30), and an exception that escapes `run_traced` is PyTutor's own failure: `INTERNAL_ERROR` ("Internal PyTutor error (please report it)") for the student, the details in the browser's console. A frame that an exception leaves gets no fake `return ↵ None` step (frames are marked on the `exception` event, unmarked on the next `line`), so the last step is where the exception was raised.
  - **Java:** see the Java failures note below.
- **Security**: shared links show warning interstitial, static analysis flags suspicious APIs (`analyzeCode`: for JS, `eval` and friends; for Python, `os`, `sys`, `subprocess`, `open`, `eval`, `exec`, … and `import js`/`pyodide`, Pyodide's bridges to the worker's JavaScript). Every engine runs the program in a Web Worker; nothing is blocked inside it (JSTutor's programs are JavaScript in a worker, a Python program can reach the same through `js`).
- **`HeapObjectType`** is an open string union — engines can emit custom types (e.g. Python's `dict`, `tuple`)
- **Target engine eagerly loaded** at startup in `main.tsx` via `getEngine(branding.languageId)`
- **Python engine** uses `sys.settrace()` in Pyodide. **The tracer works on its own terms, not the program's (#34)**:
  - **Drawing runs none of the program's code.** `_serialize_heap_object` reads a container through its own type's methods (`list.__getitem__`, `dict.items`, `set.__iter__`, …, so a subclass's `__len__`/`__getitem__`/`__iter__` don't run), an instance's attributes through `object.__getattribute__(obj, '__dict__')` (never `hasattr`/`getattr`, so `__getattr__`/`__getattribute__` don't run) and its `__slots__` through the classes' member descriptors (`_slot_values`, mangled names too; an unset slot is skipped), a function's or class's name through its type's descriptor (`_safe_name`); only real functions, methods and classes are drawn as functions (`_FUNCTION_TYPES`), so a callable instance shows its attributes. A dict key is never `str()`ed: a primitive key is its text (`_safe_repr`), an object key also a `keyValue` arrow to it. Heap objects are serialized from a queue (`pending`), not by recursion, so data nested deeper than the recursion limit is drawn, in discovery order. An int past Python's digit limit is drawn by its size, `<int with 5001 digits>` (`_int_value`).
  - **Its own builtins.** The tracer copies the builtins into its globals at load and binds the library functions it calls (`_json_dumps`, `_settrace`, `_now`, …), so a program that replaces `builtins.len`, `json.dumps` or `sys.settrace` doesn't change the tracer.
  - **CPython's recursion limit, as `python main.py` has it**: the program's module frame is depth 1 (the tracer's and Pyodide's frames below it, `_base`, don't count, nor do the comprehension frames, `_depth`), the program sees its own limit through `sys.getrecursionlimit`/`setrecursionlimit` (`_limit`, restored to the default after the run), the real limit is `_HEADROOM` (50) higher for the trace function's own frames, and a new frame deeper than `_limit` gets CPython's `RecursionError` from the tracer (`_refused`, left out of tracebacks; a one-shot profile hook, `_retrace`, turns tracing back on, since CPython turns it off when a trace function raises).
  - **A failure of the tracer itself** (any exception from `_trace_event`) stops the run (`_internal_failure`, reason `internal`): the steps so far, `{ kind: 'error', message: 'Internal PyTutor error (please report it)' }`, and the details on Pyodide's own stderr, the browser's console.
  - **The program's namespace is `{'__name__': '__main__'}`**, as CPython has main.py's: builtins come from the builtins module (exec adds `__builtins__`), so a program replacing `builtins.len` calls its own len and a variable named `list` or `max` is the program's and shown. A program may use all of CPython's builtins and Pyodide's standard library (#35): `open` reaches Pyodide's in-memory file system (a fresh one each run), `input` the stdin panel, `exit()`/`quit()`/`sys.exit()` end the program, `eval`/`exec`/`compile` work. The old copy of the builtins with `open`, `exec`, `eval`, `input`, … removed never blocked anything (a name missing from the globals is found in the builtins module), nor did the import whitelist (`_safe_import`: the import statement looks `__import__` up in the builtins, not the globals); both are gone. While it runs, `sys.__stdout__`, `__stderr__` and `__stdin__` are the program's streams too, so `sys.stdout = sys.__stdout__` brings its output back to the console.
- **Python input comes from the stdin panel (#32)** — `run_traced(source, stdin_text)` makes `sys.stdin` a `_TutorStdin` over the panel's text (named `<stdin>`, no `fileno`, so `input()` writes its prompt to `sys.stdout` and reads a line from it, as CPython does when stdin isn't a terminal; at the end, `EOFError: EOF when reading a line`). Each typed line ends with Enter, the last one too (a newline is added if the text lacks one). What a read consumes is echoed on the console where a terminal shows typing (`_echo`, `_console_add`): after the prompt, marked as input (`ConsoleLine.input`, character ranges; a line the input's newline ended gets an empty range at its end), so each step's console shows what has been read so far while `stdout` stays exactly the program's output. pythontutor.com echoes input too; CPython, reading a file, doesn't, so the CPython suite compares the console without it (`withoutInput`). Output written after the last step (`input()`'s prompt before an EOFError, a print on the line that raised, `sys.exit()`'s message) gets one more step (`_finish_output`), the last step's state with the output now; `sys.exit("message")` prints its message to stderr as CPython does.
- **Python comprehensions have frames of their own (#33)** — CPython 3.12 inlines list, set and dict comprehensions into the code around them (PEP 709): their variables become hidden fast locals of the enclosing frame, and 3.12's `frame.f_locals` can't be read there without corrupting them (in a module or class body, `LocalsToFast` after the trace function writes the merged dict back: a hidden local set to None with `RuntimeWarning: assigning None to unbound local`, or to a global of the same name; a module variable shown stale). So the tracer compiles the program through `_compile_program`: `_CompWrapper` (an `ast.NodeTransformer`) turns each comprehension into a lambda called on its outermost iterable (the parameter `.listcomp`, `.setcomp` or `.dictcomp`; the iterable still evaluated where it was), and `_name_comprehensions` renames those code objects `<listcomp>`/`<setcomp>`/`<dictcomp>`, as before 3.12 (pythontutor.com showed `<listcomp>` frames). Each comprehension then runs in a real frame, shown as `list comprehension` (`_COMP_DISPLAY_NAMES`): one step per iteration with its variables (no entry step and no step for its first line event, before any iteration; its lines aren't skipped as a statement's continuation lines), the frames of the calls it makes on top of it, and the collection it built as `return ↵`. A comprehension whose meaning depends on its scope stays inlined: an assignment expression, `super`, `__class__`, `locals`, `vars`, `dir`, `eval` or `exec` in it, `await`, or `async for`. Generator expressions have real frames already (`generator expression`). The tracer never evaluates the program's code (the old synthetic frame `eval`ed each element and filter again, so side effects ran twice); it reads a module frame's variables from `f_globals` (live, `_frame_locals`) and shows no variables for a class body with fast locals (only an inlined comprehension gives one those). A traceback leaves the comprehension frames out, as CPython 3.12 has none. A source the transform can't compile runs as written. Also (#33): a `return` event is the frame unwinding, with no `return ↵` step, unless the frame stopped at `RETURN_VALUE`, `RETURN_CONST` or `YIELD_VALUE` with no exception pending (`_returns`; a finally block or a comprehension's cleanup emits line events before re-raising), and the lines of a multi-line statement are skipped only in the statement's own frame, not a lambda's or generator expression's written inside it (`_EXPRESSION_FRAMES`).
- **#36's decisions (confirmed by the maintainer, 2026-10-19; `scripts/py-measure.ts` repeats the measurements)**:
  - **Isolation: a fresh interpreter per run (option B)**, restored from a memory snapshot. Under Node, a full Pyodide load takes 950 to 1,100 ms; taking the snapshot once (21 MB, the tracer loaded) about as long; restoring a fresh interpreter from it 70 to 180 ms. Option A (one interpreter, state reset after each run) can't undo a mutated module (`math.pi = 3`) without reloading it; option C (reset, restart only when needed) saved too little to be worth its rules.
  - **Recording: keep `sys.settrace`.** Over the corpus's 254 programs (without `limits/` and `syntax-errors/`): plain runs 166 ms in all, under a bare `sys.settrace` callback 195 ms, under a bare `sys.monitoring` callback (other code disabled) 160 ms, under PyTutor's tracer 21.7 s with 189 MB of JSON. The cost is serializing every step (#39), not the event mechanism, and `sys.monitoring` reads frames no better (the same `f_locals`).
  - **Offline viewers: stay on the CDN, and say so** (see the Export Feature's offline note): Pyodide's files are 13.8 MB, 18.5 MB as base64 in an HTML file.
- **Python runs don't leak into each other (#35, #36's decision B)** — the worker loads Pyodide once into a `PySession` with the tracer's definitions (`loadTracer`; the executor sends the tracer with `init`), takes a memory snapshot of it (Pyodide's experimental `_makeSnapshot`/`makeMemorySnapshot`/`_loadSnapshot`, pinned at 0.27.5; 21 MB), and gives each run a new interpreter restored from it (~80 ms under Node, where a full load takes ~950 ms), made ready while the student reads the previous run's steps. So nothing a program does (`math.pi = 3`, a lowered recursion limit, a module in `sys.modules`, a replaced builtin or `sys.stdout`, a file written, the working directory) reaches the next run, and no program can break a later one. If a snapshot can't be made or restored, every run gets a fully loaded interpreter (`fallbackReason`): as isolated, slower. Restored interpreters share the snapshot's string-hash seed (a set of strings prints in one order through a page session; CPython varies it per process). The analysis branch's `py-leak.mjs` pairs and #36's table are `session.test.ts`.
- **Python output is captured at the streams (#31)** — while the program runs, `sys.stdout` and `sys.stderr` are `_TutorStream`s (`io.TextIOBase` subclasses named `<stdout>`/`<stderr>`, UTF-8, strict on stdout and `backslashreplace` on stderr as CPython's, no `fileno`, so `input()` writes its prompt through them), from compiling on (a SyntaxWarning is output) until the run ends, when the tracer's own streams come back. So the real `print` (`end`, `sep`, `file`), `sys.stdout.write`, `input()`'s prompt, warnings, `traceback.print_exc()` and `contextlib.redirect_stdout` behave as in `python -u main.py`. `_write` keeps stdout's lines (`_out_lines`, split on newlines as written; a step's `stdout` drops the empty line after a final newline, `_stdout_shown`) and every line with its stream (`_console`: a line belongs to the stream that wrote its first characters), and a step carries `console` once stderr has been used, which ConsolePanel shows with stderr in red. The program is compiled as `main.py` (`_USER_FILE`) with its source in `linecache`, as CPython has it, so warnings and tracebacks name `main.py` with source lines.
- **Python reference mode** — `showReferences` store flag + `promoteToHeap()` utility converts inline primitives to heap objects, modeling Python's "everything is an object" semantics with value deduplication (reflects interning)
- `acorn-walk` is an unused legacy dependency — can be removed

## Deployment

Each language target builds to its own output directory and deploys to its own domain:

| Language | Build command | Output dir | Domain |
|----------|--------------|------------|--------|
| JavaScript | `npm run build:js` | `docs/` (`index.html` + `viewer-js.html`) | jstutor.org |
| Python | `npm run build:py` | `docs/` (`index.html` + `viewer-py.html`) | pytutor.org |
| Java | `npm run build:java` | `docs/` (`index.html` + `viewer-java.html`) | javatutor.org |

Each `build:<lang>` command emits both the main site and a sibling `viewer-<lang>.html` — the prebuilt single-file template that the Export feature fetches at runtime via `./viewer-<lang>.html`. The viewer build uses `emptyOutDir: false` so it appends to the main site's `docs/` rather than wiping it; the main build runs first.

GitHub Pages serves `docs/` for the JS site. Non-JS output directories (`docs-*/`) are gitignored and deployed separately.
